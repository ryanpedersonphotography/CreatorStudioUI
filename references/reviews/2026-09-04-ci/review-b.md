## Findings

**Material — `menubar--dark-linux.png` is not a picture of a dark menubar.** `packages/menubar/src/lib/menubar.stories.tsx:89` sets `minHeight: '100%'` on the dark wrapper. `100%` needs a definite height on the ancestor, and Ladle's `#ladle-root` doesn't have one, so the wrapper collapses to the height of the bar: the committed baseline is a ~28px black strip with "File Edit View" over ~950px of white page background. The story's own docstring says it exists to show "the system-colour fallbacks under a dark colour scheme"; ~3% of the frozen image is that colour scheme. It also renders with every menu closed (no `defaultValue`, unlike `Matrix` at line 61), so the dark *menu surface* — the one thing the package's dark path is for — is in no baseline at all. This is worse than no coverage: it is 8KB of green that reads as dark coverage. **Fix:** `minHeight: '100dvh'` on line 89 and `defaultValue="all"` on the `Menubar` at line 90 to open one menu, then one dispatch to regenerate. Two token changes, one PNG regrows to something worth diffing.

**Material — nothing waits for Radix to position a portalled menu before the shutter.** `tools/src/visual/stories.visual.mts:26-29` waits for ring-detach, a child of `#ladle-root`, and `document.fonts.ready`; `tools/src/visual/studio.visual.mts:29-30` clicks View and waits for `getByRole('menu')`. In both cases the menu element exists in the DOM before floating-ui has written its transform onto `[data-radix-popper-content-wrapper]` — the role is queryable a frame before the box is placed. `menubar--matrix` opens its menu on load, which is the worst case: no interaction to absorb the latency. With `maxDiffPixels: 0`, catching that one frame early is a full-run failure, and it will present as an unreproducible red that a dispatch "fixes". Two green runs is not evidence against this; it is two samples. **Fix:** one shared line after the existing waits in both specs — `await page.evaluate(() => new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r))))`. Two lines, no regeneration needed.

**Material — an orphan baseline is invisible forever.** `stories.visual.mts:16` derives the test list from `dist/ladle/meta.json`, so a deleted or renamed story simply stops being tested; its PNG stays in `tools/src/visual/baselines/stories/`. `visual-baselines.yml:43` runs `--update-snapshots changed`, which writes and never deletes, and line 54's `git add -A` only stages a deletion someone else made. Playwright has no orphan check. Within a month of story churn the directory stops being a manifest of what is covered, and the "reviewed as images in a pull request" promise degrades — you can no longer tell whether a 9-PNG diff is the whole set. **Fix:** a final step in `visual-baselines.yml` that fails when the on-disk PNG set doesn't equal the expected set — the specs already know both lists, so the cheapest form is a `--last-failed`-free assertion in a small `.mjs` that reads `meta.json`, adds the four studio names, and diffs against `ls baselines/**`. ~20 lines, run in both workflows.

**Material — the dispatch recipe sends you to the wrong branch.** `visual-baselines.yml:5-6` reads `git switch -c visual/<why> && git push -u origin HEAD` then `gh workflow run visual-baselines --ref visual/<why>`. That is correct only when regenerating baselines *is* the change. The actual case — a developer changed the UI on `feat/x` and CI is now red on eleven PNGs — needs the dispatch on `feat/x`, because baselines regenerated on a branch without the UI change reproduce main's pixels and CI stays red. A developer following the header literally will burn two dispatches before working that out. AGENTS.md:120 has the same gap: it says "dispatched on a branch" without saying *which*. **Fix:** change the header to `gh workflow run visual-baselines --ref <the branch carrying the UI change>` and keep the `visual/<why>` form as the secondary case. Two lines in the header, one sentence in AGENTS.md.

**Material — the documented escape hatch does not currently exist.** `ci.yml:14-16` and the last-but-three friction note both say an already-open PR whose baselines the bot just pushed needs `gh workflow run CI --ref <branch>`. `workflow_dispatch` requires the workflow file on the default branch, and `git ls-tree -r --name-only origin/main -- .github` returns only `.github/workflows/visual-baselines.yml` — `ci.yml` is not on main. The author clearly knew the rule (78a6637 seeded `visual-baselines` on main for exactly this) and did not apply it to CI. It self-heals when PR #1 merges, but it is wrong for the one PR that most needs it, and the seeding asymmetry will read as intentional to the next session. **Fix:** either land `ci.yml` on main ahead of the rest (one commit, same trick as 78a6637), or say in the header that the hatch arms once this PR merges. One line either way.

**Material — the shell has no dark baseline beyond the two studio views.** `playwright.config.mts:46` pins the `stories` project to the inherited `colorScheme: 'light'`, so all seven story baselines are light. `studio-cockpit--compact-states` — rails left and right, strips top and bottom, the states most likely to break on a token change — exists only in light. Dark tokens diverge from light at `packages/tokens/src/tokens.css:88-113` on eight variables including `--cs-border` and `--cs-surface-muted`, which are exactly what draws a rail. **Fix:** add a fourth project — `{ name: 'stories-dark', testMatch: /stories\.visual\.mts$/, use: { baseURL: 'http://localhost:61000', colorScheme: 'dark' } }` — four lines in the config, +7 PNGs (~+90KB), one dispatch. That single change is the best coverage buy on the list: it covers dark stories, dark rails and strips, and dark compact states at once. Against it: every UI change now regenerates fourteen story PNGs instead of seven — acceptable, since regeneration is one dispatch either way.

**Material — the premise that the ruleset "forces every change through a pull request" is not what the file says, and the right default for this repo is not a PR.** `.github/ruleset-main.json:6-16` has three rules: `deletion`, `non_fast_forward`, `required_status_checks`. There is no `pull_request` rule and no `required_pull_request_reviews`, so what it forces is *a green `verify` on the landing SHA*, plus `strict_required_status_checks_policy: true` meaning the branch must also be current with main. A PR is how you get that in practice, not what is required. For a solo developer with an AI pair the cost that actually bites is the round-trip: every commit waits on a 3m25s CI run before it can land, and there is no reviewer on the other side to make that wait pay. My recommendation: keep `on: push: branches: [main]` as the primary path, push to main directly, and reserve pull requests for changes that genuinely want image review — which is precisely the baseline-regeneration case the visual-baselines workflow already describes. That keeps the gate at full strength (it still runs on every main push and goes red) and spends the PR ceremony only where a human looking at a picture is the point. State that in AGENTS.md:115-121 so the next session doesn't infer that a PR is mandatory. **Cost:** a paragraph. If the plan is later upgraded and the ruleset applied, add `"bypass_actors"` for your own account so the hatch survives the enforcement.

**Minor — `threshold` is unset, so "pixel for pixel" is not what runs.** `playwright.config.mts:43` sets `maxDiffPixels: 0` with the comment "a differing pixel is a change", and AGENTS.md:113 repeats "compared pixel for pixel". Playwright's per-pixel `threshold` defaults to `0.2` (YIQ distance), so sub-threshold colour drift passes and `maxDiffPixels: 0` means "no pixel exceeds 0.2", not "no pixel differs". That default is doing real work here — it is what makes antialiasing survivable — and it should not be inherited silently. **On the sustainability question: keep 0, do not add a pixel tolerance.** The runner image, the Chromium (both `playwright` and `@playwright/test` are exact-pinned at 1.62.1 in package.json), and `animations: 'disabled'` are three independent pins, and these frames are 90%+ flat colour, so any tolerance large enough to absorb a real font shift is also large enough to hide a wrong 48px rail. The one thing that will break it is `ubuntu-24.04` being a rolling label that GitHub repatches — that failure is loud, mass, and fixed by one dispatch, which is the right trade. **Fix:** write `threshold: 0.2` explicitly beside `maxDiffPixels: 0` and correct both comments. Two lines.

**Minor — `cancel-in-progress: true` on main means commits land without a verdict.** `ci.yml:22-24` groups on `github.ref`, so two pushes to main in quick succession cancel the first. On a PR branch that is right; on main it means the intermediate commit is never verified and, because `nrwl/nx-set-shas@v5` bases `nx affected` on the last *successful* run, a cancelled run also widens the next base (safe, but it makes "what did CI check" unanswerable). **Fix:** `cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}`. One line.

**Minor — CI is not the same gate as `pnpm verify`, and three places say it is.** `ci.yml:56` runs `nx affected -t typecheck lint test build`; `package.json`'s `verify` runs `nx run-many` over everything. AGENTS.md:115 says "runs the same gate on GitHub". CI is strictly the weaker of the two, and on a `pull_request` the affected set is computed against the merge-base while the tested tree is the merge commit — so a project broken only by the *combination* of your branch and main is never typechecked. `strict_required_status_checks_policy: true` mitigates that if the ruleset is ever applied. Separately, nothing runs `nx sync:check`, so the TS project references AGENTS.md:122 tells you to keep current can drift with CI green. **Fix:** add `- run: pnpm exec nx sync:check` after line 56, and change AGENTS.md:115 to "the same gate, with the Nx targets narrowed to `affected`". Two lines.

**Minor — the write-capable job is the one with unpinned actions.** `visual-baselines.yml` grants `contents: write` (line 14) and then runs branch-controlled code: `pnpm install` lifecycle scripts, `.ladle/vite.config.mts`, the studio's vite config. Its five actions are major tags (`actions/checkout@v7`, `pnpm/action-setup@v6`, `actions/setup-node@v6`, `actions/upload-artifact@v4`), which are mutable. I would not pin `ci.yml` — it is `contents: read` and pinning five actions buys a maintenance chore against a threat that read-only permissions already contain — but I would pin these five to SHAs, because this job can push to any non-main branch. Also worth one line: `persist-credentials: false` on `ci.yml:33`'s checkout, since that job never pushes and has no reason to leave a token in `.git/config`. **Fix:** five SHAs and one line. `retention-days: 7` on both `upload-artifact` steps while you are there — 90 days is the default and neither artifact is worth a quarter.

**Minor — two small correctness slips in the specs.** `stories.visual.mts:29` and `studio.visual.mts:16` do `page.evaluate(() => document.fonts.ready)` — returning the promise means Playwright awaits it and then tries to serialise the `FontFaceSet`, which works today but is not what was meant; `await document.fonts.ready` inside the callback is the intent. And the dark studio tests never assert that dark actually applied: `emulateMedia({colorScheme:'dark'})` reaches `@media (prefers-color-scheme: dark)` at `tokens.css:101`, but if a future default ever writes `data-theme="light"` to storage on first run, `:root:not([data-theme='light'])` stops matching, the dark baseline silently becomes a light one, and the next regeneration blesses it. **Fix:** `await expect(page.locator('html')).toHaveCSS('color-scheme', scheme)` inside `open()` at `studio.visual.mts:16`. One line, and it makes the dark baselines self-describing.

**Minor — forward risk worth deciding before Write lands, not after.** `packages/menubar/src/lib/menubar.css:88` is `overflow: auto` on menu content. Today every menu fits; the moment one exceeds `--radix-menubar-content-available-height`, Linux Chromium draws a classic ~15px scrollbar and the menu's inner width jumps — a real diff, correctly caught, but you will be deciding scrollbar styling under time pressure with CI red. The manuscript surface will hit the same thing. **Fix:** decide `scrollbar-width` / `scrollbar-gutter` in `packages/tokens/src/tokens.css` deliberately now, so the first scrolling surface produces the diff you chose.

## Clean passes

**The mount signal genuinely holds, and I checked the failure mode it replaced.** `stories.visual.mts:27-28` waits for `.ladle-ring` detach then a child under `#ladle-root`, matching the friction note's measurement (attribute at ~50ms, ring gone at ~380ms). Every one of the seven story baselines I opened shows rendered content, not a spinner or a blank frame — including `studio-cockpit--compact-states-linux.png`, which correctly shows all four regions in their compact state with the `»`, `«` and chevron ways back, and the serif "Manuscript" that `Placeholder prose` at `studio-cockpit.stories.tsx:79` is supposed to produce.

**The "unstyled" look in `menubar--matrix-linux.png` is deliberate and correct, and I verified it before flagging it.** The blue system-highlight trigger and stark black border are not missing CSS: `.ladle/preview.css:3` imports `menubar.css` without the studio's `--menubar-*` bridge, `menubar.stories.tsx:5-8` says so, and `apps/studio/src/styles.css:10-27` is where the bridge lives — which is why the same component renders with the warm accent in `studio/view-open-dark-linux.png`. Two renderings of one component, both baselined, both honest.

**Cross-machine determinism has one real data point, not zero.** Run 33942098972 (`visual-baselines`, workflow_dispatch) generated and committed the PNGs on one VM at 03:31; run 33942218972 (`CI`, pull_request) compared them on a different VM at 03:34 and logged `11 passed (15.4s)` with `maxDiffPixels: 0`. That is genuine evidence the pins hold across runner instances. It is N=1 for cross-VM and does not speak to image repatching over weeks.

**The port discipline works as documented.** `reuseExistingServer: false` on both entries in `playwright.config.mts:53,62` makes Playwright refuse rather than photograph a stale dev server, and `vite preview --strictPort` closes the increment-on-busy hole for 5181. `ladle preview -p 61000` has no `--strictPort` equivalent, but the failure mode there is a 30s URL-poll timeout rather than a wrong photograph — safe, just slow.

**`fullyParallel` with two workers on shared servers is safe here.** Both servers are static; each test gets a fresh browser context; the stories use the in-memory store at `studio-cockpit.stories.tsx:10-15` and the studio tests start with empty `localStorage`. No cross-test state, and software rasterisation on a GPU-less runner is deterministic, so worker count cannot move pixels.

**A missing baseline fails the run rather than passing.** I read the installed matcher: `updateSnapshots` defaults to `"missing"` (`playwright/lib/common/index.js:576`), and `handleMissing` under that mode returns a result carrying `softError` (`lib/matchers/expect.js:12486-12491`), which marks the test failed. A new story added without a dispatch turns CI red — the gate does not silently accept new surface.

**The specs are inside the typecheck and lint gates.** `tools/tsconfig.lib.json` includes `src/**/*.mts`, and `eslint.config.mjs:84` has an `**/*.mts` block. I ran `pnpm nx run tools:lint`: it succeeded with one pre-existing warning, `tools/src/verify/cockpit.mjs:386` `'focusWithin' is assigned a value but never used` — unrelated to this change, and a warning rather than an error, so it does not gate.

**The permissions and the cost envelope are proportionate.** `ci.yml:18-20` is `contents: read` + `actions: read` (the latter needed by `nx-set-shas`). `visual-baselines.yml:22`'s `if: github.ref != 'refs/heads/main'` keeps the write-capable job off main, and `workflow_dispatch`-only means it cannot be triggered by a push. Baselines total 212KB across eleven PNGs — a rounding error in the repo, and small enough to review as images. A CI run is 3m25s on a 1× Linux runner; against GitHub Free's 2,000 private minutes a month, that is roughly 570 runs of headroom.

**The split between the two harnesses is sane, and the overlap is one cheap check.** `verify:ui` asserts numbers and behaviour — from the run log: rail widths (`48`), restored drag widths (`448 → 448`), separator state colours as oklch strings, storage keys, keyboard resize, contrast maths. The baseline asserts appearance: the composited token colours, the system font stack's glyphs, spacing, borders, and the rendered menu surface — none of which a computed-style probe can catch, because a probe reads the value you thought to ask about. The only duplication is the console/page-error check, which both do (`errors.mts:6-19` and verify:ui's "no console or page errors on load"); that costs nothing and is worth keeping in both, since either can run alone. Nothing else is doubled.

**On 2× and on hover, my recommendation is to stay out.** `deviceScaleFactor: 1` while `tools/src/verify/menubar.mjs` runs at 2× is a real asymmetry, but a full 2× baseline set triples PNG bytes and produces diffs dominated by glyph rasterisation at a different size, for a class of bug (hairlines that vanish at 1×, DPR-dependent background sizing) that has one instance in this codebase. If you want the canary, add exactly one 2× project scoped to `view-open-light` — one PNG. Hover states should not be baselined at all: they encode a mouse position, and the first layout change makes them lie.

## Verdict

The gate is well-built and the pins are real, but three things will make it lie or rot inside a month — a dark baseline that is 97% white page, an unawaited Radix positioning frame that will fire as an unreproducible red, and orphan PNGs nothing detects — and each is a two-to-twenty-line fix that costs one dispatch.
