## Findings

**Material — `packages/menubar/src/lib/menubar.css:37`, `:86`; `packages/menubar/README.md:86`. The height cap never reads Radix's available-height variable, and two places claim it does.**

`--_mb-max-h: var(--radix-menubar-content-available-height, 80vh)` is declared on `:root` (line 37). Custom properties resolve their `var()` references at computed-value time *on the element that declares them* — `:root` — where `--radix-menubar-content-available-height` is unset, because Radix writes it on the content element in the body portal, not on `<html>`. So `--_mb-max-h` computes to the literal `80vh` at `:root` and that string is what the content inherits at line 86. The Radix variable is never consulted. The `token-ok` comment on line 37 (`Radix sets this per open menu`) and README:86 (`Menus cap their height at Radix's --radix-menubar-content-available-height and scroll`) both assert behaviour the file cannot produce. This is the plan's B-19 fix; nothing in `menubar.spec.tsx` or `tools/src/verify/menubar.mjs` asserts a max-height, so it went unnoticed. Practically, menus still scroll — at a fixed 80vh rather than the space actually below the trigger, so a menu opened low in a short window can still run past the viewport edge.

Fix: delete line 37 and write the var directly where it is used — `max-height: var(--radix-menubar-content-available-height, 80vh);` in `[data-menubar='content']` — where it resolves on the element Radix stamps. Then correct README:86 or leave it true, and add a harness assertion that an open menu's computed `max-height` tracks the trigger's distance to the viewport bottom.

**Material — `packages/menubar/README.md:88-97`. "Taking it out of this repo" is a five-step procedure that leaves four files pointing at parents that no longer exist.**

Step 1 says the package "ships as source (TSX + one CSS file, no build step)". The directory you copy also contains `tsconfig.json:14` and `tsconfig.lib.json:2` and `tsconfig.spec.json`, all `"extends": "../../tsconfig.base.json"`; `vite.config.mts:10`, `setupFiles: ['../../tools/src/vitest/setup.ts']`; and `eslint.config.mjs`, which mirrors the root. None of those resolve after a copy, and none are mentioned. Step 5 names the Vitest setup honestly but only tells the reader to bring the stubs, not that the config path itself must be rewritten.

Second gap in the same procedure: `package.json` declares no `devDependencies` at all, and the README's step 5 names only `@testing-library/user-event`. `menubar.spec.tsx:1` imports `@testing-library/react`, `:4` imports `vitest`, `menubar.stories.tsx:1` imports `@ladle/react`, and `vite.config.mts:2` imports `@vitejs/plugin-react` — every one of them root-hoisted here and invisible to a copied-out package. (Root-hoisting matches `packages/shell/package.json`, so the manifest is conventional; it is the README's completeness claim that is wrong.) Also unstated: `menubar.tsx:4` imports `'./shortcuts.js'` for a `.ts` file, which needs `moduleResolution: "bundler"`/`node16` and a bundler that maps the extension — Vite and esbuild do, webpack needs `resolve.extensionAlias`.

Fix: add a step 0 — "delete `tsconfig*.json`, `vite.config.mts` and `eslint.config.mjs`, or repoint their `extends`/`setupFiles`" — and list the full dev-dependency set (`vitest`, `@testing-library/react`, `@testing-library/user-event`, `@ladle/react` if you keep the story, `@vitejs/plugin-react`) plus the `.js`-extension resolution requirement. The runtime claim ("no build step", `@radix-ui/react-menubar` the only dependency) is true and can stay.

**Material — `apps/studio/src/styles.css:14-15`. The highlighted menu row fails WCAG AA in the default theme, and nothing checks it.**

`--menubar-highlight-bg: var(--cs-accent)` over `--menubar-highlight-fg: var(--cs-surface)`. In light — the default — that is `oklch(64% 0.17 45)` under `oklch(99% 0.004 95)`: **3.49:1**, against AA's 4.5:1 for 14px text (`--cs-text-sm` = 0.875rem). Dark is fine at 6.46:1. This colour pair is the state a keyboard user sits in for every row of every menu, and it is also the open title's state (`menubar.css:65-69`). It is new with this wave — `--cs-accent` had never carried text before, only the separator's 1px rule (`packages/shell/src/lib/cockpit.tsx:289`). No spec, no harness assertion, and no entry on the plan's accepted-risk list.

Fix: bridge `--menubar-highlight-fg` to a token that clears 4.5:1 on `--cs-accent` in light — `var(--cs-p-ink)` gives 6.2:1 and reads as VS Code's selection does — or darken the light-theme accent. Then add a computed-style contrast probe to `menubar.mjs` §4 so the pair cannot regress silently.

**Minor — `tools/src/verify/menubar.mjs:237`. The plan's §9 assertion was narrowed and the narrowing is not recorded.**

Plan §9 promises "no `cs:layout:`/`cs:collapsed:` key remains for the project". Line 237 filters `Object.keys(localStorage)` on `k.startsWith('cs:collapsed:default:')` only; the two layout keys the reset actually targets (`studio-commands.ts:74-75`) are never checked in the browser. The unit spec does cover them (`studio-commands.spec.tsx:68`), so the behaviour is tested — but `disposition.md`'s "Deviations from the plan" table lists four deviations and not this one. Fix: either widen the filter to `k.startsWith('cs:layout:default:')` too, or add a row to the deviations table saying why the reload rewrites it.

**Minor — `packages/menubar/src/lib/menubar.spec.tsx:77`. `Menubar.Label` is asserted by data attribute, not by role, though the plan promised a role.**

Plan's unit list: "`Label` and `Group` render their roles". `:76` does check `getByRole('group')`; `:77` falls back to `getByText('Layout').getAttribute('data-menubar')`. Radix's `Menubar.Label` renders a plain div with no ARIA role, so the promise was not achievable as written — which makes it worth a line in the deviations table rather than a quiet substitution. If a heading is wanted for assistive tech the part needs `role="presentation"` removed and an `aria-labelledby` wiring from `Menubar.Group`, which is a real gap: `menubar.tsx:222-231` renders `Label` and `Group` as unconnected siblings, so a screen reader announcing the group never hears "Layout".

**Minor — `apps/studio/src/app/studio-menus.tsx:28-41`. The disabled seams are silent to anyone not using a mouse.**

File and Edit open menus in which every row is `disabled`. Radix skips disabled items in roving focus, so a keyboard user presses ArrowDown and nothing highlights; a screen-reader user hears three "dimmed" items and no reason. The plan called these "honest seams", and visually they are — the honesty does not reach the keyboard. Fix: one `<Menubar.Label>Coming with Write</Menubar.Label>` at the top of each, which the package already supports and which costs nothing.

**Minor — nothing asserts the keyboard path from the bar to the region toggles.** Decision 2 kept the toggles at the shelf's right specifically so the verified rail feature survives, and `menubar.mjs:104-108` proves Tab *into* the bar. Tab *out* of it — the only way a keyboard-only user reaches Navigation/Context shelf/Inspector/Top shelf — is asserted nowhere in either harness. It should work (Radix's roving tabindex makes the bar one stop), but "should" is the gap. One `ok()` after line 108: Tab again, expect focus on the Navigation button.

**Minor — `packages/menubar/src/lib/shortcuts.ts:53`. The physical-key fallback is letters-only and fails silently otherwise.** `event.code === \`Key${key.toUpperCase()}\`` produces `Key1` for a digit and `Key/` for punctuation, neither of which is a real `KeyboardEvent.code`. Harmless for today's four ⌃⌘ letters, and the docblock says "Letters also match on `code`" — but a consumer binding `⌥1` gets a shortcut that prints correctly and never fires. Fix: map digits to `Digit${key}` or narrow the fallback to `/^[a-z]$/`.

**Minor — `apps/studio/src/app/studio-cockpit.stories.tsx:41-46`. `CompactStates` did not get the `shortcuts` slot that `WritersCockpit` did**, so the story gallery has no state in which a reviewer can exercise ⌃⌘B/J/I/T. Probably deliberate for a static gallery; if so it deserves the one-line comment `WritersCockpit` got.
