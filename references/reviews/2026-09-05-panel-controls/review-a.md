## Findings

1. **Material — `collapse: 'rail'` cannot pick the rail vs. the strip size, because no panel in the shell knows its axis.** The spec says `collapse` "sets `collapsedSize` (0 for `hidden` and `peek`, the rail or strip size for `rail`)", but `orientation` reaches only the library's `Group` (`packages/shell/src/lib/cockpit.tsx:162`) and is never put on a context a panel can read — `UserLayoutContext` (`cockpit.tsx:105`) carries a listener set and nothing else. `CockpitPanel` (`cockpit.tsx:198`) therefore has no way to resolve 48px-rail vs 32px-strip from `collapse="rail"` alone. Either the prop must carry the size, or `Cockpit` must publish its orientation; the spec chooses neither, and an implementer hits this in the first hour of wave 1.

2. **Material — `collapse` and `collapsedSize` become two sources of truth for one library prop, with no stated precedence.** `pinnedPanel` returns a `Required<Pick<…, 'collapsedSize' | …>>` that is spread onto the panel (`cockpit.tsx:249-268`), and the studio spreads it on the top shelf while also passing explicit `collapsedSize={cockpitSizes.rail}` to nav and inspector (`apps/studio/src/app/studio-cockpit.tsx:113, 145`). The spec says "`pinnedPanel` keeps its meaning and takes the same prop", so `{...pinnedPanel(topHeight, strip)} collapse="rail"` sets `collapsedSize` twice. Which wins is undefined, and JSX spread order makes it an accident of authoring rather than a decision.

3. **Material — the panel's sized element is not the element the shell can style, so the slide as specified attaches to the wrong node.** `Panel` renders two divs: the outer one carries `data-panel`, the id and the sizing style (`node_modules/.pnpm/react-resizable-panels@4.12.3_…/dist/react-resizable-panels.js:2044-2059`), while `className` and the user `style` go to an *inner* wrapper (`:2063-2072`). Everything the cockpit styles today goes through `className` (`cockpit.tsx:222`) — i.e. onto the inner div. A `transition: flex` armed that way animates a node whose flex value never changes. It is fixable (rest props do reach the outer div via the `...z` spread at `:2046`, so `data-sliding` can land there and a global rule can target `[data-panel][data-sliding]`), but the spec's "arms `transition` … on the panel" hides the one detail that decides whether the wave-1 slide works at all.

4. **Material — "clip the content during the slide with `overflow: hidden`" cannot be done from a stylesheet.** The library sets `overflow` *inline* on both nodes: `"visible"` on the outer sized div (`react-resizable-panels.js:2057`) and `"auto"` on the inner content div (`:2068`). Inline style beats any class or attribute selector, and the outer div's `style` is written after the rest spread so it cannot be overridden by props either. The clip needs `!important` (or the inner div's `style` prop, which the shell does not currently pass through) — and note the cockpit's existing `overflow-hidden` class (`cockpit.tsx:222`) is already being beaten by that inline `auto` today.

5. **Material — the motion assertion asserts a property the browser will never report.** `getPanelStyles` returns `{ flexGrow: … }` (`react-resizable-panels.js:1644`); `flex-shrink` and `flex-basis` are fixed at `1` and `0` (`:2055-2056`) and never change. A `transition: flex` shorthand expands to longhands, so `element.getAnimations()` yields one `CSSTransition` whose `transitionProperty` is **`flex-grow`**, not `flex`. The spec's test — "one `CSSTransition` … whose property is `flex`" — fails against a correct implementation, which is the worst kind of failing test.

6. **Material — arming the transition on only the toggled panel produces a visible jump, because `flex-grow` is a share, not a size.** Rendered width is `total × g_i / Σg`. When nav goes 20 → 0 under a transition while its siblings re-render instantly to their new values, the denominator changes on frame one: nav's painted width steps (20/100 → 20/120 of the body) before it begins easing, and the neighbour steps with it. The spec's slide only arms the panel `usePanelToggle` acted on; to look like a slide, every panel in that group has to be armed for the same duration. This is a design correction, not a polish note — it is what the wave-1 mid-slide baselines would photograph.

7. **Material — the shell's own teardown timer cancels the transition the visual test pauses, so the mid-slide baselines silently record the end state.** The spec removes `data-sliding` "on `transitionend` or after the duration plus 50ms, whichever first", while the visual test pauses the transition and sets `currentTime = duration / 2`. A paused transition never fires `transitionend`, so the 250ms wall-clock timer fires, `transition-property` disappears, and the running transition is cancelled — the panel snaps to its final size. Playwright then polls at 0/100/250/500/1000ms comparing each frame to the previous one (`node_modules/.pnpm/playwright-core@1.62.1/…/lib/coreBundle.js:22225-22242`) and stabilises happily on that end-state frame. The baseline is committed, green, and meaningless — precisely the "subtle visual regression is known immediately" property the spec exists to buy.

8. **Material — shipping `hidden` on three regions in wave 1 breaks the focus handoff the spec claims to reuse.** `useFocusHandoff` resolves its target exclusively inside the collapsed region's own panel: `document.getElementById(id)`, then `panel.querySelector(FOCUSABLE)`, then a `section`/`[role=region]` fallback (`studio-cockpit.tsx:196-215`). With `hidden` the panel is 0px and renders nothing, so both queries return null and focus falls to `document.body` — the exact failure the hook was written to prevent, reintroduced for anyone who collapses nav from *inside* nav via ⌃⌘B. "The handoff target is the region's `PanelToggle` on the top shelf" is a rewrite of the hook to search a different panel, not a retarget. Worse, that target does not always exist: when the top shelf is itself collapsed its `Strip` renders only "Expand top shelf" (`studio-rails.tsx:41-48`), so there is no `PanelToggle` to hand focus to.

9. **Material — "existing assertions keep their count" cannot hold, and most of the breakage is in `menubar.mjs`, which the spec never mentions.** Wave 1's `hidden` default inverts every rail geometry check: `tools/src/verify/cockpit.mjs:72, 193, 201, 205, 338, 344, 397, 402` all assert 48px rails or count "Expand …" controls that no longer exist, and `tools/src/verify/menubar.mjs:191` asserts `width('#nav') === 48` after choosing Navigation from the View menu. The icon-only toggle additionally breaks `menubar.mjs:171` (`chipRing.border === '1px solid'`) and the pressed-state probe at `menubar.mjs:198-200`, which reads `borderTopColor` plus a transparent `backgroundColor` — a channel the spec replaces with "the filled segment" of an SVG glyph. The spec's testing contract names only "the cockpit harness"; the menubar harness is load-bearing here and unlisted.

10. **Material — the contrast assertion the spec promises to reuse has no mechanism for an SVG stroke.** `probe` accepts `color`, `outlineColor` or `borderTopColor` and its `drawn` check branches over exactly those three (`tools/src/verify/menubar.mjs:39-74`). "The glyph's stroke clears 3:1 … asserted by the harness as the menubar's toggles are today" needs a fourth mode reading `stroke` off the SVG child and compositing against the shelf. Reusable in spirit, new code in fact.

11. **Material — the studio bridge cannot be written: there are no CSS tokens for the rail and strip sizes, or for a shadow.** `packages/tokens/src/tokens.css` declares `--cs-focus-ring`, `--cs-motion-fast` and friends but nothing for 48px/32px — those live only as TS constants in `packages/tokens/src/lib/sizes.ts:8-16` — and the menubar bridge explicitly leaves `--menubar-shadow` on the package fallback because "no shadow token exists yet" (`apps/studio/src/styles.css:7-9`). Writing `--panel-rail-size: 48px` in `styles.css` trips token lint rule 3 (`tools/src/lint/check-tokens.mjs:119-124`, raw length in a CSS declaration) with no `--cs-*` to point at. The spec budgets exactly one new token (`--cs-motion-slide`); it needs at least three, or an explicit "left on the fallback" decision per property.

12. **Minor — `data-panel` collides with the library's own attribute on every panel.** `Panel` stamps `"data-panel": !0` on its outer div (`react-resizable-panels.js:2048`), so in the studio `[data-panel]` selects both library panels and kit parts, and `[data-panel="rail"]` nests inside `[data-panel="true"]`. The library's hit-test walk is scoped to the group's direct children (`:187-194`), so nothing functionally misfires — this is a naming cost, not a bug. But the sibling package uses `data-menubar` (`packages/menubar/src/lib/menubar.css:42`), no repo file references `data-panel` today (verified by grep across `apps/`, `packages/`, `tools/`), and renaming to `data-panel-controls` costs nothing now and a migration later.

13. **Minor — a second `kind:portable` package quietly weakens the boundary rule.** The eslint comment states the invariant it depends on: "no other project carries the tag, so a `kind:portable` package can import no workspace project at all" (`eslint.config.mjs:67-69`). With two, `onlyDependOnLibsWithTags: ['kind:portable']` starts permitting menubar ↔ panel-controls imports — the one cross-import the spec's `formatShortcut` duplication is designed to avoid, now unpoliced. The copied `manifest.spec.ts` still catches a workspace entry in `package.json` (`packages/menubar/src/lib/manifest.spec.ts:28-38`), but not a source import. A third tag value, or a lint rule naming the pair, closes it.

14. **Minor — the toolbar reorder conflicts with `STUDIO_REGIONS`, and the ordering the spec wants already exists under another name.** `STUDIO_REGIONS` is documented as "in toolbar order" and drives the toolbar's map (`studio-regions.ts:2`, `studio-toolbar.tsx:29`), while `VIEW_ORDER = ['nav','context','inspector','top']` (`studio-menus.tsx:9`) is exactly the spec's spatial order. Reordering by editing `STUDIO_REGIONS` would move the View checkbox items too, which the spec forbids; the spec should say the toolbar adopts `VIEW_ORDER` and `STUDIO_REGIONS`' comment is corrected.

15. **Minor — wave 2's `PanelEdge` gives the rail's control the same accessible name as the toolbar's toggle.** `PanelEdge`'s rail renders a `PanelToggle` whose `label` is the region name, but `studio-rails.tsx:9-12` says the current name exists specifically "so it never collides with the toolbar's toggles", and the harness relies on that: `button('Navigation')` is `getByRole('button', { name, exact: true })` (`cockpit.mjs:45`), which becomes a strict-mode violation the moment two buttons answer to "Navigation".

16. **Minor — the new preference key fails the harness's storage whitelist, and the bridge mapping list is short.** `cockpit.mjs:433-436` asserts every remaining key is `cs:theme`, a `cs:collapsed:default:*` bit, or a cockpit group; a global `cs:panel:<region>` written once the harness exercises the `When hidden` menu is none of those. Separately, the spec's bridge list omits `--cs-on-accent` for `--panel-highlight-fg` — `--cs-accent` is the fill, not the ink on it (`styles.css:16-17`).

## Clean passes

I read the spec end to end, then checked each claim against the source rather than the summary.

- **`animations: 'allow'` is right and necessary.** With the default `'disabled'`, Playwright walks `root.getAnimations()` and calls `animation.finish()` on any finite animation, re-running on every `transitionrun` (`playwright-core/lib/coreBundle.js:21132-21160`) — it skips only `playbackRate === 0`, which `pause()` does not set, so a paused transition would still be finished. `'allow'` skips that block entirely (`:21263`). And the stabilisation loop compares consecutive frames rather than demanding quiescence (`:22225-22242`), so a genuinely paused transition does stabilise. The technique works; finding 7 is about the shell fighting it, not about Playwright.
- **Accessible-name continuity holds.** Both harnesses resolve toggles by accessible name (`cockpit.mjs:45`, `menubar.mjs:33`) and `focusedLabel()` reads `aria-label ?? textContent` (`menubar.mjs:34`), so moving "Navigation" from visible text to `aria-label` keeps `cockpit.mjs:397` and `menubar.mjs:158` passing. The spec is right about this.
- **The token-lint contract block copies cleanly.** `check-tokens.mjs:107` returns on any line containing `token-ok` *before* the `var()` resolution scan, which is why `--_mb-bg: var(--menubar-bg, Canvas)` passes despite `--menubar-bg` being undeclared (`menubar.css:16-37`). A `--panel-*` block with a `token-ok` reason per line and `--_pc-*` locals used everywhere after behaves identically. Rule 1's `--_local` allowance (`:88`, `:110`) covers the locals.
- **The portable manifest spec is directly copyable** — it reads `package.json` from disk and asserts the tag triple plus no `@creator-studio/` entries under `dependencies`/`peerDependencies` (`packages/menubar/src/lib/manifest.spec.ts:22-40`), with a documented jsdom workaround. Nothing in it is menubar-specific beyond two strings.
- **Ark UI is a valid choice for React 19.** `npm view @ark-ui/react version peerDependencies` (read-only) reports `5.39.1` with `react: '>=18.0.0'`, `react-dom: '>=18.0.0'`; the workspace is on React 19.2.8. It is not installed anywhere yet, so the kit would introduce it — which the spec anticipates, and which `AGENTS.md:81-83` endorses (Ark by default; the menubar's Radix use is the documented exception). I could not read Ark's Tooltip implementation locally, since it is not in the store; the hover/focus/delay/portal claims are unverified by me.
- **The rail/strip numbers line up.** `cockpitSizes.rail = '48px'` and `strip = '32px'` (`packages/tokens/src/lib/sizes.ts:12, 14`) match the spec's 48/32, and `3rem`/`2rem` fallbacks equal them at a 16px root — worth stating in the spec, since the harness asserts exact pixels.
- **`Shortcut` is genuinely twenty lines to duplicate.** `formatShortcut` and `serializeShortcut` depend only on the local `ORDER`/glyph maps and `keyLabel` (`packages/menubar/src/lib/shortcuts.ts:19-44`) — no React, no package state. `serializeShortcut({key:'b',ctrl:true,meta:true})` gives `Control+Meta+B`, which is what `menubar.mjs:186` already asserts, so a copied implementation stays consistent with the existing assertion.

## Verdict

The shape is sound and most of the reuse claims survive contact with the code, but the spec is wrong about the one mechanism wave 1 rests on: `react-resizable-panels` sizes an outer div with `flex-grow` that the shell's `className` cannot reach, sets `overflow` inline on both nodes, and reports `flex-grow` to `getAnimations()` — so the slide, the clip, and the motion test as written each fail for a different reason, and the mid-slide baseline is additionally cancelled by the shell's own teardown timer. Add the unresolvable `collapse="rail"` size, the focus handoff that has no target under `hidden`, and the missing rail/strip/shadow tokens, and this is not yet buildable as written; the fixes are all local and none of them change the spec's architecture.
