## Findings

1. **Material — the pressed ring and the focus ring bridge to the same token, so wave 1's toolbar swap turns `verify:ui` red on an assertion the spec says it leaves alone.** The contract maps `--panel-highlight-border` (the pressed ring) to `--cs-accent` and `--panel-focus` (the focus ring colour) to `--cs-focus` (spec:155, spec:159). Those are the same value in every theme: `--cs-accent: var(--cs-p-ember)` and `--cs-focus: var(--cs-p-ember)` (`packages/tokens/src/tokens.css:56,60`), and both become `--cs-p-ember-bright` in the two dark blocks (`:96-97`, `:109-110`). `menubar.mjs:166-168` measures the numeric distance between the focused chip's `outlineColor` and its `borderTopColor` and `:174-178` requires `apart > 40` — "the ring … is not the pressed outline's colour: focus and pressed stay distinguishable". Today that passes because the pressed border is `border-ink` (`studio-toolbar.tsx:42`), nowhere near ember. Under the contract as written the distance is zero and the check fails, in both themes. The spec's reassurance names `menubar.mjs:169-173` and `:193-201` (spec:99-101) and skips `:174-178` — the one that dies. Two smaller errors ride along in the same sentence: the contract has no `outline-offset` property, while `menubar.mjs:171` requires `chipRing.offset >= 0` (today guaranteed by `CONTROL_FOCUS`'s deliberate outset, `studio-regions.ts:26-31`, whose rationale is exactly this collision); and `aria-keyshortcuts` is not "unchanged" (spec:245) because the toolbar's buttons have never carried it — only the menu items do (`studio-menus.spec.tsx:56`). A wave-1 author reads spec:245 as permission not to re-check the harness, and finds out on CI.

2. **Material — on the first failed expand a sighted pointer user sees nothing at all, and "widen the window" is the wrong remedy for the context shelf.** The `blocked` state is post-hoc: the click acts, nothing moves, and only then does the toggle carry a `hint` in its tooltip and the live region say the same (spec:229-235). The tooltip needs a 400ms hover dwell to open (spec:103) and the live region reaches screen readers only — so the writer's actual experience of the first attempt is an unchanged button, which is the defect the section exists to fix, moved one beat later. Round 2 traded a disabled control the user could see for an explanation nobody sighted receives. The hint's text is also region-wrong: nav and inspector run out of room across the body group (`friction-notes.md:84-85`, nav 160 + centre 320 + inspector 200), but the context shelf lives in the vertical centre group, where the floor is `mainMinHeight` 240 + `contextMin` 120 (`packages/tokens/src/lib/sizes.ts:22,25`) — a *short* window, not a narrow one, and widening does nothing. spec:233 hardcodes one string for all three. Nor is the clear condition decidable: "the next call that acts or the next user layout change" (spec:232) never says whether a window resize, a separator drag, or both count, so the harness assertion "the blocked hint at a narrow window" (spec:298) has no stated end state to test, and the `['resize', 900]` step (spec:320) carries a width only, so the context shelf's case cannot be staged at all.

3. **Material — the `menu` step has three behaviours and the spec shows one, so two of the nine views are not expressible.** `steps` is exemplified once as `['menu', 'View', 'Navigation']` (spec:319), a path that *selects* an item. `view-open` needs the View menu opened and left open for the picture (what `studio.visual.mts:32-38` does today with `menu: true`), and `when-hidden-open` needs `View → When hidden → Navigation` opened as a submenu and left open with its radio group showing (spec:257-259, spec:324). Those are two further modes of the same step kind — open-and-hold, and open-a-submenu-and-hold — distinguished only by path length, which the spec never states as the rule. An implementer writing `studio.visual.mts`'s interpreter has to invent the convention, and the two views most likely to be got wrong are the two whose whole content is a menu. `peek-all` has a related gap: `['hover', selector]` exists, but the zone opens after a 150ms dwell (spec:139) and `settle()` is two animation frames plus `document.fonts.ready` (`tools/src/visual/support.mts:26-33`), so nothing in the named vocabulary holds the pointer long enough, and the zone has no `data-pc` name to select (spec:128 names a hook for the edge, not for the zone).

4. **Material — the two mid-slide baselines are flaky by construction, at `maxDiffPixels: 0`.** The recipe pauses **every `flex-grow` transition**, sets each `currentTime` to half the duration, and shoots with `animations: 'allow'` (spec:325-329). `allow` un-freezes the *whole page*, not just the slide, and the config forbids a single differing pixel (`playwright.config.mts:57-62`, with the comment explicitly refusing a tolerance). The step that reaches this state is `['toggle', 'nav']`, and the toolbar toggle carries `transition-colors` over the token duration when `aria-pressed` flips — `menubar.mjs:161` already sleeps 300ms for exactly this reason ("the chip transitions its colours (outline included) for 150ms; probe the settled ring, not the interpolation"). The flex-grow transitions are pinned to a deterministic frame; the toggle's own colour interpolation is pinned to however long the Playwright round-trip took. The result is a baseline that fails intermittently on a repo whose stated thesis is that a failure means a real regression, and the first two or three false reds will teach someone to add `maxDiffPixels`.

5. **Material — the variant seam does not hold: a fourth variant edits the shell, not one map.** spec:362 promises "one entry in `PanelEdge`'s map, one part, one radio item, one composite view. Nothing existing changes." But `collapse?: 'hidden' | 'rail' | 'peek'` is a closed union in `packages/shell` that also *resolves the collapsed size* (spec:178-180), and `Cockpit.Panel` stamps `inert` on a hardcoded two of the three values (spec:193-194, spec:290). A `mini` variant at 24px therefore needs the union widened, the size resolution extended, the inert list extended, and the accepted-value validator in `usePanelVariant` extended (spec:252) — four edits in three packages before `PanelEdge` is touched. This is the seam the spec leans on to prove the foundation extends "without stripping much out", and it is the one claim in *Extension seams* that its own shell design contradicts. Naming the shell's `collapse` as `'hidden' | 'rail' | 'peek' | PanelLength`, or having the caller supply the variant→size map, would make the sentence true.

6. **Material — the "Sentences that change" list still misses four documents, including the one wave 1's headline change falsifies first.** `studio-toolbar.tsx:17-20` states "Each toggle's visible text is its accessible name and `aria-pressed` carries whether that region is expanded" — wave 1 makes the toggles icon-only with the text moved to a tooltip (spec:244-247), so that sentence is false the moment wave 1 lands, and it is not in the list (spec:270-277). Three more: `friction-notes.md:86-87` ("narrower than that the toolbar buttons do nothing") is the ground truth wave 2's `blocked` state replaces; `friction-notes.md:123-126` describes the focus handoff moving focus "to the new content's first control, or its landmark" with no mention of waiting for a slide, which wave 1 changes; and `useFocusHandoff`'s own doc block (`studio-cockpit.tsx:171-181`) says the same thing at closer range — the spec's list names only "the shell header in `studio-cockpit.tsx`", which is the diagram comment at `:11-52`, a different block. `tools/src/verify/cockpit.mjs:7-8` ("Nothing vanishes: sidebars collapse to 48px rails … each a landmark with its way back") is a fifth, outside the globs the brief named but the same class. Round 2 fixed this for `AGENTS.md` and `studio-rails.tsx` and stopped one file short of the toolbar it is rewriting.

7. **Material — wave 1 ships `peek` as a typed, tested public state that is broken until wave 3.** Wave 1's own list scopes the prop to "`rail` and `hidden`" (spec:340) and then, one line later, ships "`inert` for `hidden`/`peek`" (spec:341), and the wave-1 unit contract asserts that `Cockpit.Panel` "stamps `inert` for `hidden` and `peek` only" (spec:290). Meanwhile the shell's union carries `peek` from wave 1 (spec:178-179) while `PanelPeek` and `PanelEdge`'s zone do not arrive until wave 3 (spec:131, spec:354). So for two waves any caller of the shell — the extraction audience this kit exists for — can type `collapse="peek"`, get a panel collapsed to zero and stamped `inert`, and have no peek, no edge, and no way back except the caller's own chrome. A foundation that is "hardened before anything sits on it" should not export a value whose behaviour is a stub; type it `'hidden' | 'rail'` in wave 1 and widen it in wave 3, and drop `peek` from the wave-1 assertion.

8. **Minor — `PanelEdge` is under-specified in three ways that each cost a guess.** Its unit contract says it renders "a landmark named `Expand <region>` for `rail`" (spec:286), which contradicts spec:125, where the landmark is `aria-label={label}` (the region name, as today at `studio-rails.tsx:30`) and it is the *control inside it* that is named `Expand <region>`. Written the first way, `cockpit.mjs:205` — which locates the rail as `region { name: 'Navigation' }` containing `button { name: 'Expand navigation' }` — stops matching. Second, spec:126 requires the control to keep "today's direction chevron as its `glyph`", but the props are `variant, side, label, onExpand, children?` (spec:121) with no `glyph`, so either the kit derives the chevron from `side` (which happens to reproduce `studio-rails.tsx:16` exactly) or the studio has no way to pass one — and an opinionated skin has no override where `PanelToggle` gives it one. Third, `children` is the strip's title and is silently unused for a rail (spec:127); say so, or the first caller to pass a rail some content will wonder where it went.

9. **Minor — the strip's own control has no stated size, and the default one does not fit a 32px strip.** The spec fixes the strip's order — own control, title, then the three regions (spec:48-50) — and calls only the three "compact" (spec:255-256). `PanelToggle`'s default box is 32px and compact is 24px (spec:89-90), and the strip is 32px (`sizes.ts:14`). A default-size control in a 32px row leaves no room for the focus ring, which the contract draws at 2px with a positive offset (spec:159 and finding 1), and the panel clips (`cockpit.tsx:231`). Name the strip's own control `compact` too, or the first `top-collapsed` baseline in wave 2 will show a clipped ring.

10. **Minor — "the handoff acts only when `!sliding`" is a coin flip on where the guard goes.** `useFocusHandoff` sets `pending.current` at call time and clears it as the *first* statement of the effect (`studio-cockpit.tsx:199-200`). Under the new deps the effect fires twice — once when `collapsed` flips with `sliding` true, once when `sliding` goes false — and if the implementer adds `if (sliding) return;` after line 200 rather than before it, the flag is destroyed on the first pass and focus is never moved. The spec (spec:196-198) says the effect is keyed on both and acts only when `!sliding`, but not that the pending flag must survive the sliding pass. `cockpit.mjs:390`, `:393`, `:397` and `:402` would catch it, so the cost is a debugging session rather than a shipped bug — but one sentence removes it.

11. **Minor — two exported region orders with the same membership and nothing tying them together.** After wave 1, `studio-regions.ts` exports both `STUDIO_REGIONS` (`['top','nav','context','inspector']`, still the source of the `StudioRegion` type at `:3`) and `REGION_ORDER` (`['nav','context','inspector','top']`, spec:240-243), and the toolbar and menu move to the latter. `STUDIO_REGIONS`'s remaining consumers iterate order-independently (`studio-commands.spec.tsx:14,35,47`, `studio-menus.spec.tsx:19`), so nothing would fail if a fifth region were added to one array and not the other — and adding a region beside the text is the seam the spec itself advertises (spec:364-369). Either derive one from the other or add a one-line spec that they hold the same set.

12. **Minor — easing and the clip are asserted only by a picture, and the peek's timings have no contract property.** The motion assertion reads `effect.getTiming().duration` and `transitionProperty` (spec:303-309); it does not read the timing function, and for a CSS transition `getTiming().easing` reports `linear` regardless — the readable channel is `getComputedStyle(el).transitionTimingFunction`. The `overflow: hidden !important` clip is likewise decidable by one computed-style read during the slide, yet both are left to the mid-slide baseline (spec:328-329), which is the one artefact finding 4 says will be unreliable. Separately, `--panel-motion` is contracted as "peek timing" (spec:164) but bridged to `--cs-motion-slide`, the panel-slide token, while the peek's actual numbers — 150ms to open, 300ms to close, 6px zone — sit in prose at spec:139 with only the zone width getting a property. A skin cannot retune the peek.

## Clean passes

I checked the **wave-1 harness sleep arithmetic** by reading every sleep in `cockpit.mjs`: the two 200ms ones the spec names are at `:333` and `:354`, every other post-toggle sleep is already 300ms or more, and a 200ms slide plus the spec's duration+100ms rule clears each geometry read (`:145`, `:202`, `:397`) — so spec:299-301's claim holds as stated. I checked the **strip/toolbar name collision** the round-2 record passed clean and confirmed it survives the new slide rule: the preset swaps on `collapsed && !sliding` (spec:194-195), so the toolbar and the strip are never mounted together even mid-slide, and `cockpit.mjs:51`'s `exact: true` locators stay single-match. I checked **`pinnedPanel`'s callers** against spec:181-183 by grepping the workspace: exactly two assertions touch the dropped parameter (`cockpit.spec.tsx:145` and `:149`), the nested story is the one the spec names (`cockpit.stories.tsx:54`), `cockpit.spec.tsx:77` and the doc example at `cockpit.tsx:21` pass one argument and are unaffected — the spec's inventory is complete. I checked the **same-commit arming** claim (spec:208-213) against the CSS Transitions model: a transition starts when the after-change style names the property and the value differs from the before-change value, and the before-change style's own `transition` is not consulted, so stamping `data-sliding` in the layout effect of the commit that changes `flex-grow` genuinely is early enough. I checked the **shortcut-spam** case in `packages/menubar/src/lib/shortcuts.ts:113`: `event.repeat` is guarded, so a held ⌃⌘B fires once and neither the arming nor the live region can be driven by key auto-repeat. I checked the **`Tab` ordering assertions** against the toolbar's reorder to `REGION_ORDER`: `cockpit.mjs:358` takes `#top button` `.last()`, which becomes `Top shelf` instead of `Inspector` but is still the bar's last button, and `menubar.mjs:159`'s accepted set already lists all four names, so the reorder costs no assertion. I checked the **storage whitelist**: `cockpit.mjs:435` is the one that needs the variant key shape, and the earlier assertion at `:117-119` runs before any variant could be written, so spec:267's singular "the storage assertion" is right by luck rather than by statement.

## Verdict

Round 2 closed the mechanism gaps it was aimed at, but three of its fixes bought their precision by moving the cost somewhere the spec does not look: the contract now names two ring colours that resolve to the same token and break a live contrast assertion in wave 1, the no-room state is explained through two channels that neither reach a sighted pointer user on the first attempt nor say the right thing for the context shelf, and the `{ view, steps, screenshot? }` descriptor gained a vocabulary that cannot express the two menu views it was written to bound. Underneath those, the spec still promises a variant seam its own closed `collapse` union contradicts, and still ships `peek` as a typed shell state that is inert-and-gone for two waves — both fixable in a sentence each, and both the kind of claim a later wave will build on before anyone re-derives it.
