Read enough. Writing the review.

## Findings

1. **Material — the kit's DOM hook is a name the panel library already owns.** Spec:49 gives every part a `data-panel="<part>"` hook, the direct analogue of the menubar's `data-menubar`. But react-resizable-panels stamps a bare `data-panel` on **every** panel element it renders (`node_modules/.pnpm/react-resizable-panels@4.12.3.../dist/react-resizable-panels.js:2048`), and this repo already recorded that fact in its own review history (`references/reviews/2026-09-02-skeleton/reviewer-b-conventions.md:38`). In the studio, the kit's parts render *inside* those very elements. It is not a crash — the library only walks direct children of a group (`dist/react-resizable-panels.js:188,194`) — but every `[data-panel]` query in a harness, a spec, or a future skin now matches five cockpit panels plus every kit part, and `data-disabled` (spec:71's disabled state, `dist:194`) is a second name the library reads on the same axis. A writer debugging in devtools sees one attribute meaning two things. The spec should pick `data-panel-controls` or `data-pc` and say so once; renaming after wave 1 is a skin rewrite.

2. **Material — the slide is specified against an element and a property that do not exist.** Spec:126–128 says "`react-resizable-panels` sizes panels with inline flex values" and arms `transition: flex var(--cs-motion-slide) ease-out` on "the panel". The library renders **two** divs: the outer one carries the id, the rest props, and the sizing style — which is `flexGrow` alone, not `flex` (`dist:1644`, `dist:2052–2056`) — while the consumer's `className` is handed to the *inner* div (`dist:1961`, `dist:2060–2063`), whose `flexGrow` is a constant `1`. A transition declared the obvious way, through `Cockpit.Panel`'s `className`, therefore animates nothing. Worse, `transition: flex` is a shorthand that expands to three longhands, so spec:170–171's assertion — "`getAnimations()` on the panel returns **one** `CSSTransition` … whose property is `flex`" — cannot pass as written; the implementer will discover this and rewrite the assertion to whatever the browser actually returns, which is how a motion contract silently becomes a tautology. Name the outer element, name `flex-grow`, and say through which prop the rule reaches it: `Cockpit.Panel` today destructures a fixed prop list (`packages/shell/src/lib/cockpit.tsx:198–235`) and forwards no arbitrary attributes, so `data-sliding` and `data-collapse` need explicit new props.

3. **Material — nothing decides what a hidden panel is to the keyboard or a screen reader.** Spec:36 says a `hidden` panel leaves "nothing" on screen and spec:80 says `PanelEdge` "renders nothing" for that variant — but `PanelEdge` is the *edge*, not the panel's content. The shell's own contract is that a collapsed panel keeps its children mounted (`cockpit.tsx:183`), and `collapsedSize: 0` gives a zero-width box whose descendants remain in the tab order and in the accessibility tree; clipping does not remove either. So a writer who hides Navigation and presses Tab lands inside an invisible panel, and a screen reader still reads its tree. The spec must decide the mechanism — unmount, `hidden`, `display: none`, or `inert` — and it must decide it in wave 1, because it changes whether the panel's content can hold state across a hide. Related and also unstated: when a hide is fired from the menu or a shortcut, focus is elsewhere, `aria-pressed` changes on a control nobody is on, and nothing is announced at all.

4. **Material — wave 1 ships a strictly worse studio than today and orphans the assertions that prove it.** Spec:146 puts nav, context and inspector on `hidden` in wave 1, with `PanelEdge` and the preference not arriving until wave 2. That deletes the rails from the shipped product for a whole wave, directly contradicting the stage doc ("a rail or strip state on every edge (nothing vanishes)", `AGENTS.md:38`) and the shell's own header comment (`apps/studio/src/app/studio-cockpit.tsx:22`), neither of which the spec says it is amending. It also strands live harness coverage: `tools/src/verify/cockpit.mjs:344` asserts exactly three "Expand …" buttons, `:205` asserts the rail is a landmark carrying the way back, and `:284` clicks "Expand navigation". Spec:169's promise that "existing assertions keep their count" cannot hold when the state they assert is unreachable — `rail` is in the shell in wave 1 but has no route through the studio until the menu lands in wave 2. Either wave 1 keeps today's `Rail`/`Strip` on the three regions and changes only the toolbar, or the spec says plainly which assertions die and why the regression is acceptable.

5. **Material — window resize while hidden removes a safety net the harness was built around.** Two harness blocks exist precisely because a narrow window squeezes a panel the user never touched: `cockpit.mjs:246–266` (a nav reset collaterally rails the inspector) and `:269–296` (at 560px the nav mounts railed and its expand cannot act). Both depend on the squeezed panel leaving a visible rail with a control on it. Under `hidden` the panel vanishes instead, `usePanelToggle.expand()` returns false silently (`packages/shell/src/lib/use-panel-toggle.ts:139–149`), and the writer gets a toolbar button that does nothing, with no visible state and nothing announced. The spec never mentions resize. It needs a ruling: does a window-caused collapse fall back to `rail` regardless of the preference, does the toggle become disabled when the group has no slack, or is silent refusal accepted as risk?

6. **Material — the three "ways back" are not three.** Spec:36 lists the way back from `hidden` as "the panel's icon on the top shelf, its ⌃⌘ shortcut, the View menu". Two of those live on the top shelf, and the top shelf is itself collapsible (⌃⌘T) to a strip whose only control is "Expand top shelf" (`apps/studio/src/app/studio-rails.tsx:39–46`). Collapse the shelf and every panel's icon and the whole menu bar go with it; the shortcut is the sole survivor. Today that is tolerable because each panel keeps its own rail. Under a `hidden` default it means one keystroke can leave a writer with three vanished panels and no visible affordance for any of them. Either the strip must carry the region toggles, or the spec must state that the shortcut is the real single way back and accept it.

7. **Material — three of the four states the skin must show have no story, no baseline, and no assertion.** Spec:71 names pressed/unpressed, hover, `:focus-visible` and disabled as states the skin must distinguish. Spec:190's story matrix is "four sides × pressed, dark" — side and pressed only. The visual config disables animations and photographs static pages (`tools/src/visual/playwright.config.mts:57`), so no hover or focus state is ever captured, and spec:160–164's unit list asserts none of them either. A change that flattens the hover fill, drops the focus ring, or makes disabled indistinguishable passes every listed check. Worse, `PanelToggle`'s props (spec:60–63) have **no `disabled` prop at all**, so a state the skin is required to render has no way to be entered. This is the single clearest instance of the brief's "a change that would pass every test and still look wrong".

8. **Material — the visual harness has no seam for "put the studio in this state", and the spec's baseline plan needs one.** Spec:176–179 asks for "the studio in every variant of every region, hidden and shown" plus paused mid-slide frames. The shared view list that both the spec and the prune workflow read is `{ view, menu }` and nothing else (`tools/src/visual/baselines.mjs:32–35`), and the spec file loops over exactly those two fields (`tools/src/visual/studio.visual.mts:27–42`). Adding variant states means changing the shape of that record and its consumers — an edit to a contract whose comment exists to stop the picture set and the behaviour parting ways. The spec also never bounds the count: three regions × three variants × two states × two schemes is 36 studio baselines before the mid-slide frames, and every one is a PNG a human reviews in a pull request. Name the descriptor change and the intended count, or say which combinations are dropped.

9. **Material — the seams do not reach the example the spec uses to prove them.** Spec:207 offers "a new panel (a character card beside the text)" as the extension test and claims it needs only a `Cockpit.Panel`, a `PanelToggle` and a preference key. Three things block it. `StudioCockpit` takes exactly five fixed `ReactNode` slots and hard-codes the nesting (`studio-cockpit.tsx:54–68, 96–150`), so a sixth region is an edit, not an add. `PanelToggle`'s glyph is derived from `side` (spec:60, 65–66) with no override, so a second right-hand panel renders a button pixel-identical to Inspector's, distinguished only by its tooltip. And `PanelPeek` is `position: fixed` at the **window** edge (spec:79, 89) while `rail` renders "at the place the panel was" (spec:37) — two coordinate systems in one part, and a card beside the text is at neither. The variant map (spec:84) is a genuine seam; the panel set and the glyph are not.

10. **Material — the rail's content contradicts itself, and today's strip loses its title either way.** Spec:37 says the `rail` variant shows "its icon at the head, **no letters**". Spec:78 says `PanelEdge`'s `children` are "the toggle plus, **for a shelf, the title**". A writer implementing wave 2 must guess. The live code answers the question a third way: `Rail` shows the region's initial letter and `Strip` shows the full title text (`studio-rails.tsx:32–34, 43`), so "no letters" is a silent removal of shipped content, and the top shelf — pinned to this variant (spec:45) — is the one place the title is load-bearing, because its strip is all that is left of the menu bar. Decide it per axis and say what today's strip loses.

11. **Material — two contract properties have no source, and the rail's size lives in two unit systems with nothing checking they agree.** The bridge list (spec:114–117) maps nine `--cs-*` tokens plus the cockpit sizes and one new motion token — it names no source for `--panel-shadow` or `--panel-z`, and the token package has neither a shadow nor a z-index token (`packages/tokens/src/tokens.css` has only `--cs-p-motion`). Since a raw `rgb(0 0 0 / 0.3)` in the studio stylesheet fails the token lint, wave 3 needs a shadow token the spec never lists. Separately, the contract's `--panel-rail-size: 3rem` / `--panel-strip-size: 2rem` (spec:108) describe the same rail as `cockpitSizes.rail = '48px'` / `strip = '32px'` (`packages/tokens/src/lib/sizes.ts:12,14`), which is what `collapsedSize` actually receives — a px value the shell type forbids expressing in rem. Nothing asserts the CSS rail and the panel's collapsed width are the same number, and at any non-default root font size they are not. The visual config's own comment warns about exactly this ("a tolerance wide enough to absorb a font shift also hides a wrong 48px rail", `playwright.config.mts:53`).

12. **Material — first paint is decided, the second paint is not.** The spec is right by construction that a fresh load cannot flash, because the transition is only armed while `data-sliding` (spec:128) and the library reads the stored layout during render. But `usePanelToggle` runs a mount reconcile that calls `handle.expand()` in an effect when a panel came up collapsed against a memory of "open" (`use-panel-toggle.ts:111`) — after the first paint, and not through `toggle()`. Today that is a visible 48px→288px jump; under `hidden` it is 0→288px, on every load at a window narrow enough to clamp. The spec never says whether the reconcile arms `data-sliding` (a slide the writer did not ask for, on every load) or does not (a jump). Say which, and put it in the motion assertions — it is the one animation a writer sees without touching anything.

13. **Minor — the preference key makes its own named door a migration.** Spec:137 proposes `cs:panel:<region>`, global, with "per project variants" listed as a door (spec:200). Every other per-project key in this repo puts the project id in the second segment (`layoutKey` → `cs:layout:<projectId>:<group>`, `collapsedKey` → `cs:collapsed:<projectId>:<panelId>`, `packages/contracts/src/lib/layout-store.ts:30,41`), so walking through that door changes the key's shape and silently drops every writer's stored variant unless someone writes a migration. A `panelVariantKey(region)` that reserves the slot — or a name that does not read like "the panel's state", which is what `cs:panel:nav` sounds like beside `cs:collapsed:default:nav` — costs nothing now. Relatedly, spec:154 says reset is untouched, so "Reset layout" will not clear the variants; that may well be right, but `studio-commands.ts:85` explicitly instructs the next author to revisit the key list, so the spec should record the decision rather than leave it to be rediscovered.

14. **Minor — Ark UI arrives in a parenthetical, inside the portable package, and brings unlisted work.** Spec:68–70 adds Ark "as the kit's external dependency if it is not one yet". It is not: no `@ark-ui` or `zag` appears in any manifest in this workspace. So wave 1 introduces the repo's first Ark dependency and puts it in a `kind:portable` package whose whole promise is a short extraction list — the menubar's is one runtime dependency (`packages/menubar/README.md:99–100`) and this kit's README must now say the same about a considerably larger tree. Two consequences go unnamed: the shared jsdom setup currently stubs `scrollIntoView` and pointer capture for Radix (`packages/menubar/README.md:110–112`), and Ark's tooltip will want its own stubs and timer handling before spec:161's "tooltip appears on hover and on focus" can pass; and no listed test dismisses the tooltip, so WCAG 2.1 SC 1.4.13's dismissible-and-hoverable requirement is asserted for neither the tooltip nor the peek overlay, though the peek's design (Escape, 300ms grace, focus holds it open — spec:38, 90–92) already satisfies it.

15. **Minor — small things a reader must guess.** Spec:141–143 reorders the toolbar to "spatial order left to right: Navigation (left), Context shelf (bottom), Inspector (right), Top shelf (top)" — that is not a left-to-right order, it is the existing `VIEW_ORDER` (`studio-menus.tsx:9`), and the constant the toolbar actually maps is `STUDIO_REGIONS`, whose doc comment claims to be "in toolbar order" (`studio-regions.ts:1–2`). Say which constant changes. Spec:38 and 89 never say whether a hidden panel's separator can still be dragged open — it is still in the DOM, still focusable, still announced as "Resize navigation" (`cockpit.mjs:54`) for a panel that is not there. Spec:38's 8px `--panel-peek-zone` sits exactly where a manuscript scrollbar and a left-margin text selection live, with no suppression rule. And spec:148's radio labels are "Vanish · Rail · Peek" while the stored values are `hidden | rail | peek` — harmless, but spec:137 validates on read without ever naming the accepted set.

## Clean passes

I checked the **variant table against the owner's rulings** (spec:36–42 vs the plainest-default and changeable-from-the-menu rulings) — three variants, `hidden` first, reached from View, and spec:40–42's promise that names, shortcuts and menu items are identical across variants is the right invariant and is unit-testable as stated. I checked the **portability constraint** by reading `packages/menubar/README.md:8–11, 92–120` and `AGENTS.md:84–89` against spec:48–54: the `kind:portable` tag, the manifest spec, the `:root` contract block with standalone fallbacks and one `token-ok` per line, and the duplicated `formatShortcut`/`serializeShortcut` (spec:94–96, with the duplication recorded in both packages) all match the established pattern exactly. I checked the **reduced-motion rule** (spec:132–133): `prefers-reduced-motion` appears nowhere in the repo today (grepped all `.css/.ts/.tsx/.mjs/.mts` outside `node_modules`), so this is new and correct in shape — the state change survives, only the duration goes to zero, and a zero-duration transition genuinely produces no `CSSTransition`, so spec:173's "no animation exists" is decidable. I checked **the accessible-name continuity claim** (spec:143–144) against the harness's actual queries: `cockpit.mjs:51,183,265,294` select by accessible name with `exact: true`, and an icon-only button carrying `aria-label={REGION_TITLES[region]}` keeps every one of them matching. I checked the **mid-slide screenshot technique** (spec:177–179) against `playwright.config.mts:56–62`: the global `animations: 'disabled'` is a per-assertion-overridable default, so `animations: 'allow'` on those two shots works, and a paused animation is stable under Playwright's consecutive-screenshot stabilisation. I checked the **`hidden`/`rail` collapsed sizes** against the shell: `pinnedPanel` and the panel props already accept a `collapsedSize` (`cockpit.tsx:186–188, 246–264`), so spec:121–123's `collapse` prop is genuinely additive at that layer.

## Verdict

The shape is right — three variants over one control set, a variant map that a fourth entry extends rather than edits, and a motion contract asserted by numbers rather than by feel is a real advance on "it looked fine". But the foundation is not yet the smallest hardenable thing: the slide is specified against the wrong element and the wrong property, the DOM hook collides with the library underneath, nothing decides what a hidden panel is to the keyboard or a screen reader, and wave 1 as written removes the rails from the shipped studio while leaving the assertions that prove them in place.
