## Findings

1. **Material — the disarm rule's drag clause selects an attribute that does not exist in 4.12.3, and the corrected selector would still miss most drags.** Spec line 224 disarms on "a `pointerdown` on a `[data-resize-handle]` inside the group, heard at capture". `data-resize-handle` occurs **zero** times in `node_modules/.pnpm/react-resizable-panels@4.12.3*/…/dist/react-resizable-panels.js`; v4 renamed the part to `Separator`, which renders `data-separator` (`dist:2226`) and `role="separator"` (`dist:2232`). So the listener matches nothing and the clause is dead code — a drag started within the slide window fights a running `flex-grow` transition, which is exactly the A11 failure the clause was added to close. Substituting `[data-separator]` is not sufficient either: `dist:261-279` inflates the grab rect to `resizeTargetMinimumSize.fine` (10px, `dist:1606`) centred on the element, and `Cockpit.Separator` draws a 1px line, so roughly 4.5px on each side of the visible separator starts a drag while the event target is a `[data-panel]`'s content — the same inflation `cockpit.tsx:100-107` already documents ("the 1px separator element is never the event's target"). The motion assertion that would have caught this, "none during a drag" (spec:311), passes vacuously, because a drag with no preceding toggle has nothing armed to find. The cheap fix is to drop the selector entirely and disarm on any capture-phase `pointerdown` inside the group element.

2. **Material — the pressed-state `fill` channel is unreadable as specified, in both harnesses, so the assertion that replaced the deleted border is red against a correct implementation.** Lines 97-98 state "the segment's computed `fill` is `currentColor` when pressed and `none` when not", line 100-101 makes it "one computed-style read", line 284 makes it a jsdom unit assertion and line 295 a browser one. I ran this repo's installed jsdom (27.4.0) against `<rect fill="currentColor">` and `<rect fill="none">`: `getComputedStyle(rect).fill` returns `""` in both cases, while `getAttribute('fill')` returns the literal. In a browser the opposite failure applies — `getComputedStyle` returns *resolved* values, so `fill: currentColor` comes back as the resolved colour (`rgb(…)`), never the keyword the spec names. Both assertions therefore fail on a correct component, and this is the entire second machine-readable channel that round 2 (A6/B3) put in place of the pressed border it was asked not to delete. Two sentences fix it: the unit test reads `getAttribute('fill')`, and the harness asserts `fill !== 'none'` — or, if the intent is to prove the segment is painted in the button's ink, compares the resolved `fill` to the button's computed `color`, which is the same probe input line 330 already uses.

3. **Minor — the motion integers name three of the four toggleable regions and omit the top shelf.** Lines 303-312 give "for the navigation in the body group that is two … and the same two for the inspector, and the main and context in the centre group", but never state the pair for the root group `[top, body]`, even though `top` is a region with its own ⌃⌘T, its own toggle, and its own harness coverage at `cockpit.mjs:141-156`. The number is two, and it is derivable from the sources the spec already cites — collapsing `top` takes the non-last-panel branch at `dist:937-955` with `pivotIndices: [0, 1]`, the reduction loop at `dist:767-786` shrinks `top`, and `body` (no `maxSize`) absorbs the whole delta — but an implementer writing "the expected integer per region" from this paragraph has to derive it rather than read it, which is precisely what round 2's A2 disposition promised to remove.

4. **Minor — the focus handoff's new `!sliding` guard has one correct placement and one silent-failure placement, and the spec does not say which.** Line 196-198 says `useFocusHandoff` "keys its effect on `collapsed` and `sliding` and acts only when `!sliding`". In the existing effect the very first statements are `if (!pending.current) return;` then `pending.current = false;` (`studio-cockpit.tsx:199-200`). If the new guard goes after that clear, the commit in which `collapsed` flips with `sliding` true consumes the pending flag and returns, and the later commit where `sliding` goes false finds `pending.current === false` and does nothing — focus falls to `document.body` on every hide, which is the A8 regression, and `cockpit.mjs:390` ("moves focus to the strip control") turns red. Only placing the guard *before* line 199 preserves the flag across the slide. One clause in the spec — "the guard precedes the pending check, so the flag survives to the commit that ends the slide" — makes it unbuildable-wrong instead of coin-flip.

5. **Minor — two toggles in the same group during one slide overwrite each other's `data-sliding="self"`, so the first panel silently loses its clip.** Lines 209-216 have each `Cockpit.Panel` stamp `"group"` on every `:scope > [data-panel]` sibling and `"self"` on its own element, with the clip scoped to `"self"` only. `data-sliding` holds one value, so if nav is mid-slide (⌃⌘B) and the inspector is toggled inside the 200ms window (⌃⌘I), the inspector's layout effect rewrites nav's element to `"group"` and nav's `overflow: hidden !important` disappears mid-animation — the content reflow the clip exists to hide. Panels in different groups are safe, because the arming sets are disjoint (`nav`/`center`/`inspector` in the body group versus `main`/`context` in the centre group), so this is only reachable for the nav-and-inspector pair. The harness will not catch it: the loop at `cockpit.mjs:331-334` becomes 300ms per click under the spec's own sleep rule, so the slides never overlap there. Two separate attributes, or a `data-sliding` plus a `data-sliding-self`, removes the collision.

6. **Minor — the new stylesheet has no route into either consumer, because `packages/shell` exports no CSS.** Line 204 puts the slide rule in `packages/shell/src/lib/cockpit.css` "imported by the studio's `styles.css` and `.ladle/preview.css`". Both files import CSS by package specifier — `@import '@creator-studio/menubar/menubar.css'` at `apps/studio/src/styles.css:3` and `.ladle/preview.css:4` — which works only because `packages/menubar/package.json` carries an explicit `"./menubar.css": "./src/lib/menubar.css"` export. `packages/shell/package.json`'s `exports` block has just `.` and `./package.json`, so the import the spec names does not resolve until that entry is added. The `@source '../packages'` lines in both files are Tailwind's class-scanning directive, not a CSS import, so they do not cover it. One added export entry, named in wave 1 beside the file.

## Clean passes

I read the round-1/round-2 record and the revised spec, then checked each changed mechanism against the workspace's own installed sources rather than the spec's description of them.

- **`sliding` can be set only on a call that acted, and the mount reconcile does bypass it.** `collapse()` returns early when the panel is already collapsed (`use-panel-toggle.ts:128`), then reads the panel back through `sync()` and branches on the result (`:131-136`); `expand()` returns early unless collapsed (`:140`) and likewise reports `!collapsed` (`:143-148`). Both give a post-hoc acted/didn't inside the same handler, so `setSliding(true)` is reachable exactly where the spec says. The reconcile at `:111` calls `handle.expand()` — the library's imperative handle — not the hook's `expand()`, so it cannot set `sliding`; and because nothing is armed at mount, its `flex-grow` change starts no transition, which is what B12's "no slide on the reconcile" needs.
- **The library commits layout through React state, so the arming and the `flex-grow` change land in one commit.** `collapse()`/`expand()` route through `a()` → `j()` (`dist:474-482`), which replaces a module-level map and emits `groupChange`; each `Panel` reads its style through `useSyncExternalStore` on that event (`dist:2033-2037`, `getSnapshot` at `:2029-2032`). Both that update and the hook's `setCollapsed`/`setSliding` are raised synchronously inside one handler, so React batches them into a single render and a single commit. I also checked for the flush hazard that would kill the transition: nothing in the library reads layout during that commit — its only layout effect is the isomorphic `q` at `dist:1989`, whose dependency array (`:2013-2025`) is unchanged by a collapse, and `Ke` at `dist:1871` is cleanup-only; the `offsetWidth`/`getBoundingClientRect` sites (`dist:70, 144, 148, 997, 1368`) all sit on the pre-mutation imperative path or in the ResizeObserver, not between mutation and layout effects. Adding `transition-property` in the same style change as the value change does start a transition, per the CSS Transitions after-change-style rule, and the spec's own "read your computed `transition-duration` after arming" step (line 220) forces the recalc that makes it deterministic.
- **`Group`'s `elementRef` is real and reaches the element.** Destructured at `dist:1600`, merged with the internal ref at `dist:1628`, applied as `ref: w` on the group div at `dist:1785`, and typed `elementRef?: Ref<HTMLDivElement | null>` at `react-resizable-panels.d.ts:87`. It is a distinct prop from the `groupRef` `Cockpit` already passes (`cockpit.tsx:160`), so both can coexist.
- **`:scope > [data-panel]` is exact.** The group renders `<div data-group>{children}</div>` (`dist:1777-1800`) and each panel renders its outer `data-panel` div directly (`dist:2043-2059`); `Cockpit` interposes only a context provider (`cockpit.tsx:156-167`) and `Cockpit.Panel` renders `ResizablePanel` with no wrapper (`cockpit.tsx:219-235`). Nested cockpits sit inside a panel's *inner* div (`studio-cockpit.tsx:105, 119`), so the root group's scope yields `#top`/`#body` and the body group's yields `#nav`/`#center`/`#inspector`, with no leakage either way.
- **The clip and the rest-prop route are right.** Rest props spread first on the outer element (`dist:2046`) before `data-panel`/`id`/`ref`/`style`, so `data-collapse`, `data-sliding`, `data-collapsed` and `inert` all land there; the outer element's only child is the library's inner div, whose inline `overflow: 'auto'` (`dist:2068`) is what needs `!important`, and `> *` therefore hits exactly one element. The outer element's constant style block (`en`, `dist:2083-2094`) contains no `visibility`, so the shell's `visibility: hidden` from `data-collapsed` needs no `!important`.
- **`transitionend`/`transitioncancel` do bubble, and `getAnimations()` keeps a paused transition.** Both events are `bubbles: true`, so a listener on the group element hears them from its direct panel children; the `propertyName === 'flex-grow'` filter excludes the separator's `transition-colors` (`cockpit.tsx:286`) and the toolbar chips. A paused animation remains current and in effect, so it is still returned by `getAnimations()` — the re-arm loop at line 222-223 holds, and `Animation.finish()` in the baseline recipe (line 328) fires `transitionend`, which is what releases the disarm.
- **The two-per-toggle integer is correct for every region I could derive.** Collapsing `nav` takes the non-last branch (`dist:937`, `f` false) with `pivotIndices: [0, 1]`, shrinking `nav` and growing `center`, whose only constraint is `minSize` (`studio-cockpit.tsx:118`), so the reduction loop at `dist:767-786` breaks with `inspector` untouched. `inspector` is last, but the fast path at `dist:938-947` requires every preceding panel to be collapsible *and* already collapsed, and `center` is neither, so it falls to `le` with `pivotIndices: [1, 2]` — again two. `context` is last in the centre group and fails the same test on `main` (`studio-cockpit.tsx:120`, not collapsible), giving `main` + `context`. Arming panels whose share does not change is harmless: no value change, no transition, which is what "and no other panel does" asserts.
- **`aria-disabled` does open the tooltip.** Zag's tooltip trigger guards every open path on `prop("disabled")` (`tooltip.connect.mjs:52, 59, 66, 76, 85, 92, 97, 101`), a machine prop defaulting to `false` (`tooltip.machine.mjs:25`); it never consults the DOM's `aria-disabled` or a native `disabled`, and browsers dispatch pointer and focus events on `aria-disabled` elements normally. So round 2's A4 fix is sound — with the one unstated condition that the kit must not forward its own `disabled` prop to the Tooltip root. Two caveats on provenance: `@ark-ui/react` and `@zag-js/*` are **not installed in this workspace** (zero hits in `pnpm-lock.yaml`, nothing under `node_modules`), so I read a sibling repo's copy at version 1.41.2, not the 1.31.1 my predecessor cited, which exists in neither place. ## Verdict

The two mechanisms the round-2 revision was built on both hold: the grown binding can set `sliding` only on calls that acted and the mount reconcile genuinely bypasses it, and arming in a layout effect of the library's own commit does start the transition, because the library commits through `useSyncExternalStore` and reads no layout in that commit. What did not survive checking are two of the details attached to them — the drag disarm targets an attribute v4 does not have and would still miss most drags once corrected, and the pressed-state `fill` assertion returns an empty string under this repo's jsdom and a resolved colour in a browser, so the channel that replaced the deleted border is red against a correct build; both are one- or two-sentence repairs, and neither reopens an architectural question.
