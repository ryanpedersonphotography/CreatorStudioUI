Verification is complete across all eight areas of the brief. Here is the round-2 review.

## Findings

1. **Material — `usePanelToggle` has no DOM access of any kind, so "arms `data-sliding` on the whole group" is not buildable from where the spec puts it.** The spec's slide rests on line 166: "`usePanelToggle` arms `data-sliding` on the whole group for a programmatic toggle." The hook's only handle is `usePanelCallbackRef()`'s `PanelImperativeHandle` (`use-panel-toggle.ts:82`), which is `{collapse, expand, getSize, isCollapsed, resize}` and nothing else (`react-resizable-panels.d.ts:225-250`); `GroupImperativeHandle` is `{getLayout, setLayout}` (`:37-55`). The hook is not given the panel's `id` either (`use-panel-toggle.ts:81`), so it cannot even `getElementById`. Reaching the group means adding `elementRef` — which `Panel` does support and merges onto the outer div (`react-resizable-panels.js:1966, 1978, 2051`) — to `CockpitPanelBinding`, which today is `Pick<PanelProps,'panelRef'|'onResize'> & {onUserLayout}` (`cockpit.tsx:172`), and then walking `.parentElement`; or moving the arming into `Cockpit`, which owns the `Group` and its `id` (`cockpit.tsx:161`). The spec names neither, and the choice matters for finding 7: arming must be scoped to the group element's **direct children**, because a `querySelectorAll('[data-panel]')` from the group reaches nested groups' panels too.

2. **Material — "one `CSSTransition` per panel in the group" is false, and fails against a correct implementation.** The motion assertion (line 231) counts one transition per panel, but a collapse only changes the shares of the panels around the pivot. `collapse()` routes through `a(collapsedSize)` with `pivotIndices: [S, S+1]` for a non-last panel (`react-resizable-panels.js:952`), and the distribution loop `break`s the moment the delta is absorbed (`:767-784`). In the body group `[nav, center, inspector]`, collapsing nav hands the freed share to `center`, which has only a `minSize` (`studio-cockpit.tsx:118`) and absorbs all of it; `inspector`'s entry in the layout is never touched, its inline `flexGrow` is unchanged, and no transition starts on it however it is armed. The assertion should be "one per panel whose share changed", and it also needs an element filter: `document.getAnimations()` during a toggle click additionally returns the toolbar chip's colour transitions, which the menubar harness already documents as running for 150ms (`menubar.mjs:161`).

3. **Material — `inert` on a collapsed panel's content has no element to attach to, and applied "for every variant" it makes the rail's expand button unusable.** Lines 52-53 say the shell marks "a collapsed panel's content wrapper `inert` and `visibility: hidden` … for every variant". There is no such wrapper the shell owns: `Panel` renders the inner content div itself and passes it only `className` and the consumer's `style` (`react-resizable-panels.js:2061-2069`), so no attribute can be placed on it, and `CockpitPanel` renders `children` straight through (`cockpit.tsx:232`). Worse, in wave 1 the studio uses `rail` everywhere and swaps children on collapse (`studio-cockpit.tsx:115, 132, 146`), so the collapsed content *is* the `Rail`/`Strip` and its `ExpandButton` (`studio-rails.tsx:18-25`) — marking it inert removes the way back the spec's own line 46 calls non-negotiable. Two things need fixing: `inert` belongs on the outer element via rest props (which do reach it, `:2046`) and only for `hidden`/`peek`; and `Cockpit.Panel` has no way to know it is collapsed today — the single `panelRef` is owned by `usePanelToggle` — so it needs a `collapsed` input the spec does not name.

4. **Material — a natively `disabled` toggle can never show the reason the spec puts in its tooltip, and it breaks the focus target the spec calls always-present.** Lines 79-80 and 178-180 make `disabled` + `disabledReason` the answer to the no-slack case, with the reason "shown in the tooltip". Zag's tooltip trigger opens on `onPointerMove` and `onFocus`, and both return early when the machine is disabled (`@zag-js/tooltip@1.31.1/dist/index.js:64, 88`); independently, Chromium suppresses pointer events on disabled form controls, so the trigger never sees the move. The tooltip that explains the disablement is therefore the one tooltip that cannot open. The same `disabled` also removes the button from the tab order, which collides with line 204's "that target always exists": the handoff's second target is exactly the toggle that would be disabled on a narrow window, and focus falls to `document.body` again — the failure round 1 raised as A8. Use `aria-disabled` with a no-op activation handler and keep the button focusable and hoverable.

5. **Material — the tooltip is never stated to be portalled, and the shelf clips it.** `PanelToggle` lives on the top shelf, whose panel content div carries the cockpit's `overflow-hidden` class and the library's inline `overflow: auto` (`cockpit.tsx:231`, `react-resizable-panels.js:2068`), inside a 48px-tall pinned panel (`studio-cockpit.tsx:97`); a tooltip rendered in place is clipped to that box and invisible. The menubar solved precisely this and says so — "menus render in a body portal, and inherit from body, so a bar-scoped value would never reach them" (`menubar.css:10-12`) — and the panel-controls contract is put on `:root` for the same reason (spec line 63), so the omission is an oversight rather than a decision. Ark ships `Portal` for it (`@ark-ui/react@5.39.1/dist/components/portal/portal.d.ts`). This also changes the hover and focus baselines the spec promises at lines 239-240: both states open the tooltip, so those pictures will contain a floating-ui-positioned overlay, which this repo already records as "an unreproducible red against a zero-pixel tolerance" (`support.mts:21-25`). The stories need a way to suppress the tooltip, or `--panel-motion`-style delay control, or the baselines will be the flaky ones.

6. **Material — wave 1 deletes the one non-colour pressed-state channel the harness can actually measure, and replaces it with something the probe cannot assert.** `menubar.mjs:192-200` reads `borderTopColor` on the pressed toggle, requires `drawn` (a non-zero, non-`none` border), a ≥3:1 ratio against the shelf, and an unpressed counterpart below 3:1 with a transparent fill; `menubar.mjs:171` separately pins `chipRing.border === '1px solid'`. `tokens.css:16-21` documents that outline as the deliberate second channel for WCAG 1.4.11 and says "the menubar harness measures it". The icon-only `PanelToggle` has no border in the contract table (lines 128-140), and the spec's replacement is "pressed and unpressed distinct by the filled segment" (line 97) asserted "by the menubar harness's probe with its new SVG mode" (line 248). `probe` computes contrast ratios (`menubar.mjs:39-74`); it cannot assert that a path is filled. Either the toggle keeps a measurable border, or the spec names a different assertion — the computed `fill` of the segment element being non-`none` plus its own ratio — and says so where it currently promises the probe.

7. **Material — the clip rule reaches neighbour panels, including the manuscript's scroller.** `[data-panel][data-sliding] > * { overflow: hidden !important }` (line 170) applies to every armed panel, and the spec arms the whole group. In the centre group that includes `main`, whose inner div is the manuscript's scroll container — the library's inline `overflow: auto` (`react-resizable-panels.js:2068`) beats the cockpit's `overflow-hidden` class (`cockpit.tsx:231`), which is why round 1 needed `!important` in the first place. Forcing `overflow: hidden` on a scrolled element for 200ms while its box grows shrinks the scroll range, and a clamped `scrollTop` is not restored when `overflow` returns; a writer hiding the context shelf would lose their place in the manuscript. I did not run a browser to measure this (read-only brief), and the cheap fix removes the question entirely: only the panel being collapsed or expanded needs clipping, so scope the rule to the toggled panel rather than to every armed one.

8. **Minor — `pinnedPanel` losing its parameter breaks two of the shell's own assertions and a story, and the spec names only the studio.** Line 154 says "`pinnedPanel(size)` drops its `collapsedSize` parameter and the studio stops passing `collapsedSize` itself". Three other call sites exist: `cockpit.spec.tsx:145` asserts `pinnedPanel(topHeight, strip).collapsedSize === strip` and will not compile, `cockpit.spec.tsx:149` asserts the returned object with `toEqual` including `collapsedSize`, and `cockpit.stories.tsx:54` uses `pinnedPanel(topHeight)` for the nested shelf and would silently move from `cockpitSizes.collapsed` (`'0px'`, `sizes.ts:10`) to the library's `'0%'` default unless it gains `collapse`. The visual outcome is the same at zero, but `cockpit--nested` is a committed baseline in both schemes, so the change should be deliberate rather than incidental.

9. **Minor — the spec asks for a fourth probe mode and then removes the reason for it.** Line 86 says the glyph uses `currentColor` "so the contrast probe reads `color`", and line 98 says the probe "gains a `color`-on-SVG reading … a fourth mode beside `color`, `outlineColor`, `borderTopColor`". Only one can be true. With `currentColor`, `probe(button, 'color')` already works unchanged — `getComputedStyle(el).color` is the painted value and the `of === 'color'` branch starts its backdrop walk at the element itself (`menubar.mjs:56`), so no new mode is needed. The catch is that `drawn` is hardcoded `true` for `color` (`menubar.mjs:71`), so a later change setting an explicit `stroke` would pass unnoticed. If the intent is to measure what is actually painted, the fourth mode is `of: 'stroke'` with a matching `drawn` branch — which is a one-line addition, and worth naming as that rather than as a `color` mode.

10. **Minor — `:focus-visible` and the focus-opened tooltip both require keyboard modality, which `page.focus()` and `fireEvent.focus` do not supply.** The spec asserts "tooltip appears on hover and on focus" as a unit test (line 216) and photographs `:focus-visible` as a baseline (line 95, 239). Zag gates focus-opening on `isFocusVisible()`, which is `currentModality === "keyboard"` fed only by real keyboard events (`@zag-js/focus-visible@1.31.1/dist/index.js:156-158`, and the trigger's `onFocus` guard at `@zag-js/tooltip/dist/index.js:66`); `currentModality` initialises to `null`. Both the unit test and the visual story must reach the button by Tab, not by focusing it, or the tooltip never appears and the ring baseline may bake in without one.

11. **Minor — the disarm rule has no stated behaviour when the safety check finds a running animation, and the mid-slide recipe pauses one transition where the group now has several.** Line 172-174 disarms "after a safety delay of five times the duration that first checks `getAnimations().length === 0`, so a transition a test has paused stays armed" — but says nothing about what happens next, and if the check simply skips, `data-sliding` and its `!important` clip persist for the session, which would then make "none exist during a drag" (line 233) fail on the next drag. Separately, line 244 pauses `animation` singular, while the same document's line 231 establishes that a toggle produces several; pausing one and letting the others finish yields a stable but meaningless frame — the round-1 A7 failure mode in a new dress. The recipe needs to pause every `flex-grow` transition in the group.

12. **Minor — the contract table has no properties for the toggle's own box, so "only the contract block carries `token-ok`" is not reachable as tabled.** The token lint flags any raw length in a CSS declaration outside `packages/tokens/src/` (`check-tokens.mjs:116-122`) and exempts only lines containing `token-ok` (`:103`), which is why the menubar turned every raw length into a contract property — 22 `token-ok` lines, all in the block. The panel-controls table (lines 128-140) covers colours, radius, rail/strip, zone, shadow, motion and z, but nothing for the button's size, padding, gap or the `compact` variant the strip needs. Those are additional contract rows, not a design change, but the spec budgets the block and the bridge precisely and this omission makes both counts wrong.

13. **Minor — three harness sleeps now equal the slide duration exactly.** `cockpit.mjs` sleeps 300ms after most toggles, which clears a 200ms slide, but `cockpit.mjs:333` and `:354` sleep exactly 200ms between consecutive toggle clicks — a coin flip against `--cs-motion-slide: 200ms`, where the second click lands as the first transition ends and re-arms a group mid-flight. The spec's seam claim at line 284 ("the slide reads one token; the motion assertions read the same token") is therefore incomplete: 39 `sleep(300)` and 3 `sleep(200)` calls in `cockpit.mjs`, plus 17 and 9 in `menubar.mjs`, are a second undeclared dependency on that token's value.

## Clean passes

I read the round-1 record and the revised spec end to end, then checked each revised mechanism against the installed source rather than against the spec's summary of it.

- **Rest props do reach the sized element.** `Panel` destructures its known props and spreads the remainder first on the outer div, before `data-panel`, `id`, `ref` and `style` (`react-resizable-panels.js:2044-2059`), so `data-collapse` and `data-sliding` land where the spec needs them. The consumer's `style` and `className` go to the inner div only (`:2063-2069`), so the spec is right that a global rule is the only route.
- **A transition on `flex-grow` of that element does animate a programmatic collapse.** The outer style pins `flexBasis: 0` and `flexShrink: 1` as constants (`:2055-2056`) and `getPanelStyles` supplies only `flexGrow` plus a drag-time `pointerEvents` (`:1644-1650`), so size is purely the grow share and `flex-grow` is the single animatable longhand — matching the spec's corrected rule and assertion property.
- **Nothing in the library cancels or rewrites the inline style mid-transition.** The group's `ResizeObserver` observes the group element and only those panels that pass `onResize` (`:1491`); the group branch recomputes layout only when `ne({group})` — the sum of panel extents along the group's own axis (`:70`) — actually changes, which a sibling's slide inside the same group does not do. Panel-level callbacks route to `jt`, which reads `offsetWidth` and calls the consumer's `onResize` without touching layout (`:1362-1372`); `usePanelToggle.onResize` then calls `isCollapsed()`, which reads the stored layout percentage, not the DOM (`:1003-1006`), so the shell's `collapsed` state does not flap across the slide. Re-renders during the slide recompute the same final `flexGrow`, and writing an unchanged computed value neither restarts nor cancels a transition.
- **`visibility` is free on the inner element.** Its inline style is `maxHeight`, `maxWidth`, `flexGrow`, `overflow`, the consumer `style` and `touchAction` (`:2064-2073`) — `visibility` is not among them, so a stylesheet can set it without `!important`. The problem in finding 3 is the missing selector hook and the rail, not the property.
- **The orientation context resolves rail vs strip correctly under nesting.** Each `Cockpit` renders its own provider around its `Group` (`cockpit.tsx:156-167`), and the nested cockpits sit *inside* `Cockpit.Panel id="body"` and `id="center"` (`studio-cockpit.tsx:105, 119`), so `top` reads the root's `vertical` → strip, `nav`/`inspector` read `horizontal` → rail, `context` reads `vertical` → strip. That reproduces exactly today's `strip`/`rail`/`strip`/`rail` assignment (`studio-cockpit.tsx:97, 111, 129, 142`) with one source, as A1/A2 asked.
- **`onlyDependOnLibsWithTags: []` does forbid every workspace import here.** The installed plugin has a dedicated branch: an empty array plus a target with any tags reports `emptyOnlyTagsConstraintViolation` (`@nx/eslint-plugin@23.2.0/dist/src/rules/enforce-module-boundaries.js:453-465`), so it means "only untagged projects", not "no constraint". Every workspace project is tagged (studio, contracts, menubar, shell, tokens, tools), so the set of legal targets is empty. It is also a safe change today: `packages/menubar/src` contains no `@creator-studio/` import at all, so the existing portable package does not newly fail lint.
- **A story's `meta` does reach `dist/ladle/meta.json`.** Ladle parses a top-level `Story.meta = {…}` assignment statically, requires an `ObjectExpression`, and JSON round-trips it (`@ladle/react@5.1.1/lib/cli/vite-plugin/parse/get-storyname-and-meta.js:24-40`); the build merges it into each story entry as `meta` and writes the file (`generate/get-meta-json.js:34-40`, `cli/build.js:29-33`), and the committed `dist/ladle/meta.json` already shows a `"meta": {}` slot per story. `stories.visual.mts` can read a hover or focus target from it — the only edit needed is that `baselines.mjs:48` currently keeps just `Object.keys`, so it needs a second export carrying the values.
- **The tokens spec is buildable under the token lint.** `check-tokens.mjs:83` treats everything under `packages/tokens/src/` as the token package and returns before rules 2-4 (`:109`), so a spec file there may hold `'48px'` and `'32px'` literals; `packages/tokens/vitest.config.mts` exists, and `menubar/src/lib/manifest.spec.ts:15-19` is a directly copyable precedent for reading a repo file under jsdom with `resolve(import.meta.dirname, …)` rather than `new URL`.
- **Ark's tooltip defaults match the spec's numbers.** `openDelay` defaults to 400 and `closeOnEscape` to `true` (`@zag-js/tooltip@1.31.1/dist/index.d.ts`, `TooltipProps`), so lines 87-88 and the "Escape dismisses" unit test need no overrides; `@ark-ui/react` is 5.39.1 with peers `react >= 18` / `react-dom >= 18`.
- **The strip's four toggles do not collide with the toolbar's.** `Strip` renders only while the shelf is collapsed and the toolbar lives inside the expanded shelf (`studio-cockpit.tsx:98`), so `button('Navigation')` — `getByRole('button', {name, exact:true})` at `cockpit.mjs:45` — never sees two. The rail's control keeps the distinct `Expand <region>` name (`studio-rails.tsx:21`), as A15 asked.

## Verdict

The revision fixes what round 1 found — the outer element, the `flex-grow` property, the whole-group arming, the orientation source, the tags rule and the size tokens are all correct against the installed sources — but it introduced a new layer of mechanisms that were specified without being traced back to code, and four of them do not exist: the hook told to arm the group has no DOM handle, the content wrapper told to go `inert` is the library's own div and taking it out kills the rail's expand button, the disabled toggle cannot show the tooltip that justifies it, and the transition count the motion test asserts is not what a collapse produces. None of this changes the architecture, and every fix is local — an `elementRef` on the binding, `inert` scoped to `hidden`/`peek` on the outer element, `aria-disabled` instead of `disabled`, a per-changed-panel count, a portal on the tooltip and a narrower clip — but the spec is not yet buildable as written, and the mid-slide baseline it is built to protect is still recording something other than a mid-slide.
