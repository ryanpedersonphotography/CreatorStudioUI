I have what I need — the spec, the round‑1 record, and the code and harnesses it claims consistency with. Writing the review.

## Findings

1. **Material — the wave‑1 `inert` rule blanks the rail, which is wave 1's only collapsed state.** Spec:52 has the shell mark a collapsed panel's content `inert` and `visibility: hidden` "while collapsed … for every variant", and spec:259 lands that in wave 1. But "collapsed" in this shell means *at its collapsed size*, explicitly including a rail or strip (`packages/shell/src/lib/use-panel-toggle.ts:21-24`), and the studio renders the rail **into the panel's own children slot** (`apps/studio/src/app/studio-cockpit.tsx:115`, `:98`, `:132`, `:146`). Spec:53's "a rail's content is the edge, not the panel" is an assertion, not a mechanism — the shell has one content slot and the `Rail` is in it. Since wave 1 uses `rail` everywhere (spec:257), the rule as written makes every collapsed panel's `Expand <region>` button invisible and unfocusable, which is the way back. `cockpit.mjs:205`, `:211`, `:344`, `:352`, `:398`, `:402` all fail, and a writer who collapses the nav cannot reopen it except by shortcut. The rule needs to key on the *variant* (`hidden`/`peek` only), not on `isCollapsed()`.

2. **Material — the element `inert` is supposed to go on does not exist, and the reason given for choosing `inert` is false in the studio.** Spec:156 stamps `inert` and `data-collapsed` "on the content wrapper". The library's typings are explicit that `className` and `style` reach the nested inner div while every other prop reaches the outer one (`react-resizable-panels.d.ts:276,370`; source at `dist/react-resizable-panels.js:2046-2063`), and `Cockpit.Panel` renders `<ResizablePanel>{children}</ResizablePanel>` with no wrapper of its own (`packages/shell/src/lib/cockpit.tsx:219-235`). So an *attribute* can only land on the outer element — the same element spec:157 correctly targets for `data-*` — and the shell must either accept that or add a wrapper div, which changes the flex/overflow chain. Separately, spec:52 justifies `inert` over unmounting because "state survives"; the studio's preset already swaps children on collapse, so state does not survive today and nothing in wave 1 changes that. The consequence is a check that cannot run: spec:226's "a hidden panel's content is `inert` and its controls are not in the tab order" has no content to inspect in the studio, in any wave, unless the spec says the preset stops swapping.

3. **Material — the toggle's pressed state loses the only channel a machine can read, and the harness assertions that prove it break in a wave the spec says breaks none.** Today `menubar.mjs:193-201` (run in both themes, `:203` and `:309`) asserts that a pressed toolbar toggle's *border* clears 3:1 against the shelf while an unpressed one's does not and its fill is exactly transparent — WCAG 1.4.11 in a number — and `:169-173` asserts `border === '1px solid'` with the ring outside it. Wave 1 replaces those four buttons (spec:190-193) with a kit toggle whose pressed channel is "the filled segment" of an SVG plus `--panel-highlight-bg` (spec:133, :247-248), and whose contract has no toggle border at all (spec:132 scopes `--panel-border` to "rail edge, peek edge"). Spec:229's reassurance — "wave 1 changes none of the rail assertions because the rails stay" — is true and beside the point; it is the *menubar* chip assertions that die. Worse, the replacement is unmeasurable: the glyph is one `currentColor` (spec:85-86), so `color` reads identically pressed and unpressed, and "pressed and unpressed distinct by the filled segment" (spec:248) is asserted by nothing but a PNG a human looks at. That is precisely the class of regression this spec exists to catch.

4. **Material — the slide's selector and its arming contradict each other, and the motion assertion is not a number.** Spec:163 writes the rule as `[data-panel][data-sliding]`, a compound selector matching one element carrying both attributes, while spec:166 says `usePanelToggle` "arms `data-sliding` on the whole group". Those cannot both be true: on the group element the selector must be a descendant one, and a descendant selector then reaches *nested* cockpits — the centre group lives inside the body group's centre panel (`studio-cockpit.tsx:118-134`), so toggling the nav would arm main and context too. Nor does the hook have the reach the spec attributes to it: `usePanelToggle` holds one panel handle (`use-panel-toggle.ts:82`, `:158`) and no group DOM node; whoever stamps the attribute must be `Cockpit`, and the spec never says so. This lands on spec:230-231, which asserts "one `CSSTransition` per panel in the group" — a relational count that resolves to 3, 5, or 2 depending on which of the readings above the implementer picks, so a run's transcript cannot decide it. Name the element, the stamping component, and the expected integer per group.

5. **Material — "no room" has no source for its boolean, disables the wrong direction, and leaves the menu item and the shortcut doing exactly what the rule was written to fix.** Spec:178-179 disables the toggle "whenever the group has no slack for that panel". Nothing in the shell can answer that question without acting: slack is discovered only by calling `handle.expand()` and reading the panel back (`use-panel-toggle.ts:139-149`), and there is no group-resize subscription that would recompute it as the window narrows. The rule is also stated over the group's slack rather than over the panel's state, so read literally it disables the toggle for a panel that is *shown* on a narrow window — locking the writer out of the collapse that would free the room. And it disables only the toggle: `StudioCommand` already carries an unused `disabled` field (`studio-commands.ts:20`), yet the View check item and the ⌃⌘ shortcut are left to fail silently, with no live-region announcement either, which is the original defect wearing a different hat.

6. **Material — wave 1 has grown past the smallest hardenable foundation, and two of its additions cannot be proven where they land.** Three items belong in wave 2. The strip's four compact toggles (spec:46-48, :194) are a studio surface change, not a kit primitive, and they break `cockpit.mjs:145` and `:226` (which assert exactly one "Expand top shelf" control) and `:390` (which asserts the focus handoff lands on that control) — the handoff takes the *first* focusable in the panel (`studio-cockpit.tsx:203`) and the spec never fixes the strip's internal order. The live region (spec:54) and the `inert` rule (spec:52) both exist to serve `hidden`, which has no route through the studio until wave 2 (spec:257: "the studio uses `rail` everywhere"), so wave 1 ships them with no harness path. What must come *forward* instead is the wave‑2 focus handoff target (spec:202-204): the moment the strip carries toggles, the handoff's search changes behaviour, so its second target should land with the strip or the strip should wait. On the owner's ruling: deferring `hidden` to wave 2 respects it — the plainest variant is still the shipped default, and wave 1's rails are scaffolding rather than a competing default. The dodge is that the foundation being hardened in wave 1 is the *rail* path, and the default path gets one wave of hardening, not two.

7. **Material — the live region is mounted inside the thing it has to outlive, and what it says for the top shelf is undecided.** Spec:54 puts a polite live region "on the shelf". The shelf collapses to a strip (`studio-cockpit.tsx:97-99`), and under spec:52 a collapsed panel's content is `visibility: hidden`, which removes a live region from the accessibility tree — so ⌃⌘T followed by ⌃⌘B announces nothing, which is the exact case (menu or shortcut, no control under the pointer) the region was added for. The studio already has the right home: the `shortcuts` slot renders inside the region context but outside every panel, for precisely this reason (`studio-cockpit.tsx:63-67`, `:95`). The wording is also unresolved for the shelf itself: the top shelf is pinned to `rail` and never hides, so "Top shelf hidden" would be false, and the spec's template (spec:54) gives no alternative for a region that collapses to a strip rather than vanishing.

8. **Material — the `{ view, steps }` descriptor cannot express three of the seven named views, and the 14 baselines miss wave 1's own surface.** Spec:239-240 defines `steps` as "menu paths, toggles, a resize". `peek-all` needs the pointer parked in a hover zone and held there (spec:118), which is none of those. `slide-nav-hide` / `slide-nav-show` need an animation paused at `currentTime = duration / 2` **and** a per-assertion `animations: 'allow'` override of the config default (`playwright.config.mts:57-58`) — a screenshot option, not a step, so the descriptor needs a fourth field. There is also a consumer problem the spec doesn't name: `baselines.mjs` is imported by the prune script under plain Node (`baselines.mjs:119-135`), so `steps` must be serialisable data with an interpreter in `studio.visual.mts:27-42`, not callbacks. On the set itself, the arithmetic is right (7 views × 2 schemes = 14) but the selection is not: there is no baseline of the collapsed top shelf strip — wave 1's most visible change, and the surface where four new toggles now sit beside a title in 32px — and none of the `When hidden` submenu (spec:197), since `view-open` shoots the View menu closed-submenu. Both would then be asserted by nothing.

9. **Material — three documents still say the opposite of what the spec plans, and the spec names only a fourth.** "Nothing vanishes" is on the record in `AGENTS.md:38` (the Stage section, "a rail or strip state on every edge (nothing vanishes)"), in the shell's header comment (`studio-cockpit.tsx:22-28`, which also promises "the way back is there by construction whatever a caller passes"), and in the rails file's own rationale (`studio-rails.tsx:4-11`, "The preset renders these itself; a caller cannot leave them out"). Wave 2 makes `hidden` the default (spec:37, :263) and none of those sentences is listed as changing — the spec names only `studio-regions.ts:1`'s "in toolbar order" comment (spec:192). `AGENTS.md:114` is a fourth: it describes the visual gate as "every Ladle story and two studio views", which spec:242 takes to seven. A wave‑2 author reading AGENTS.md as ground truth will find it flatly contradicting the spec it was handed.

10. **Material — the peek's anchoring is the seam the spec uses to prove extensibility, and it has no mount point.** Spec:116 positions the overlay absolutely on the anchor's edge, the anchor being the cockpit body group so a panel beside the text peeks at the text's edge (spec:113-114). Every panel clips: the shell sets `overflow-hidden` on the inner element (`cockpit.tsx:231`) and the library sets `overflow: auto` there inline (`dist:2068`) and `overflow: visible` on the outer one (`dist:2057`). So an overlay rendered inside the panel it stands in for is clipped away, and one portalled out needs the anchor's rect measured and re-measured on every group resize. Spec:283's promise that a different skin only redefines `--panel-*` is fine; this one is the seam that actually decides whether the character-card example works, and it is a positioning strategy the spec leaves to the implementer.

11. **Minor — the rail's icon changes meaning, and the spec does not say what it becomes.** Today the rail's control carries a directional chevron, documented as "which way the region opens, drawn as a glyph the accessible name does not repeat" (`studio-rails.tsx:15-16`, `:22`). Wave 2 replaces the rail's control with a `PanelToggle` (spec:106), whose glyph is the panel-rectangle with the `side` segment filled or outlined (spec:83-85), and spec:196 describes the change only as "the icon in place of the letter" — the letter being the separate `<span>` at `studio-rails.tsx:32-34`, not the chevron. So the chevron's meaning is dropped silently, and on a rail the new glyph renders in its *unpressed* form, pixel-identical to the same region's unpressed toggle on the shelf, with only the accessible name distinguishing them. Decide whether the rail's icon is the toggle glyph, the chevron, or the toggle glyph with a direction, and say what `studio-rails.tsx:15-16`'s comment becomes.

12. **Minor — five things a reader must guess.** `VIEW_ORDER` is a module-private const in `studio-menus.tsx:9` and the toolbar is a different file, so spec:190 requires a move or an export the spec doesn't name — and spec:191 calls it "the panels' spatial order" while the constant's own comment calls it VS Code's Appearance order, "sidebars first, the bar itself last" (`studio-menus.tsx:8`), a rationale the spec neither adopts nor amends. Spec:238's story `meta` mechanism is real — Ladle's manifest carries a per-story `meta` object (`dist/ladle/meta.json`) — but `baselines.mjs:45-57` returns `Object.keys(...)` and throws the meta away, so a new export is needed and unnamed, as are the story names for the hover, focus and disabled shots (spec:260 lists them only as "by meta"). Spec:189 says "the key list in `studio-commands.ts` says so" without saying whether that means `layoutKeys`'s comment (`:71`) or the `useStudioCommands` doc block whose "revisit the list" instruction is the thing being answered (`:85-86`). Spec:98 calls the contrast probe's SVG reading "a fourth mode" when `color` is already mode one (`menubar.mjs:39`, `:75`) and reads `currentColor` off an SVG unchanged; what actually needs adding is the drawn-ness predicate the probe deliberately skips for `color` (`menubar.mjs:70-72`), without which a glyph whose stroke is removed entirely still passes. And spec:194 says the strip's toggles sit "beside its title" without fixing their order against the existing `Expand top shelf` control — which is what decides finding 6's focus assertion, and whether the strip carries five controls or four.

## Clean passes

I checked the **slide's property and element** against the library build: `getPanelStyles` returns `{ flexGrow }` and nothing else (`dist/react-resizable-panels.js:1643-1646`), and the outer div spreads rest props before stamping `data-panel` (`:2046-2048`) while `className`/`style` are documented as going to the nested inner div (`react-resizable-panels.d.ts:276,370`) — so spec:160-163's naming of `flex-grow` on the outer element, and spec:157's `data-*` forwarding, are both correct, and the round‑1 A3/A5/B2 fixes hold. I checked the **`data-pc` rename** by grepping the same build: the library stamps `data-panel` (`:2048`) and *reads* `data-disabled` when walking panels (`:194`), so both names were genuine collisions and both are avoided. I checked the **orientation resolution** by comparing spec:152-154 against the live tree: root and centre are `orientation="vertical"` and body defaults to horizontal (`studio-cockpit.tsx:96,105,119`; `cockpit.tsx:114`), which maps top→strip, context→strip, nav/inspector→rail — exactly the `collapsedSize` values passed today (`:97,111,129,142`), so `collapse` is a faithful one-for-one replacement. I checked the **size tokens** against `packages/tokens/src/lib/sizes.ts:12,14` (48px/32px) and `tokens.css` (only `--cs-p-motion: 120ms` at line 41), confirming all three new tokens are genuinely new and the unit spec at spec:145-147 has two real numbers to compare. I checked the **separator-as-way-back** claim (spec:205-206): the nav and inspector separators are undisabled and named (`studio-cockpit.tsx:117,136`), so dragging a zero-width panel open is a real route, while the shelf's separator is `disabled` (`:103`) — which costs nothing because the top shelf is pinned to `rail`. ## Verdict

The revision fixed what round 1 aimed at — the slide now names the right element and property, the DOM hook no longer collides, the sizes have one source — but the two fixes that were meant to close the accessibility and no-room gaps were written as prose rather than as mechanisms, and both invert in practice: `inert` on every collapsed panel blanks the rail's own way back in the wave that ships only rails, and the disabled rule has no way to compute its boolean and leaves the menu item and shortcut untouched. Wave 1 has also grown a studio surface (the strip's four toggles) that breaks three live assertions the spec says it does not touch, while the pressed state's one machine-readable channel is traded for a filled glyph segment that only a human reading a PNG can tell apart.
